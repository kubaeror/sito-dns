# Current 2.0 Claim Matrix (Phase 3 / rc.1 candidate)

This is the current evidence matrix for the **2.0.0-rc.2 candidate** (workspace
version `2.0.0-rc.2`; the final Phase 3 gate and tag are recorded on the
release PR). Historical audits and release
notes are leads, not evidence; the
[audit 6 claim matrix](audit6-claim-matrix.md) records the earlier v1.9.3/1.9.4
snapshot and keeps its historical banner. This page maps the Phase 2 claims
(WP-2.1 through WP-2.13) and the Phase 3 verification claims (WP-3.1 through
WP-3.4, where evidenced at the rc.1 candidate) to implementation, named tests
and current operator documentation. The security evidence is in the
[Phase 3 security review](phase3-security-review.md).

Status vocabulary:

- **Delivered** — implemented on this tree and covered by the named test or
  check.
- **Delivered with residual** — the control exists, but the listed limitation is
  explicit and operator-visible.
- **Deferred** — not implemented; do not plan around it for this claim.

## Residuals carried forward

- **Bundled parental data:** `adult` and `gambling` are 40-entry minimal
  fallbacks, not a maintained dataset. The 2.0 mapping stays per-group and
  off by default; wider coverage requires `[integrations.lists]` or a manual
  catalog/custom list. The catalog ships no dedicated parental filter.
- **P1-1 DNAME:** decoded as `RData::Unknown`; `validate`/`strict` fails closed
  with SERVFAIL/AD=0. Accepted for rc.1 as an availability/compatibility
  limitation; re-review by 2027-01-31 or a hickory upgrade.
- **Fuzz evidence:** the nightly 600 s/target smoke is active and the workflow
  matrix is fixed; a five-target 60 s smoke passed, but the 24-hour five-shard
  campaign is a deferred release-checklist item and has not been run for rc.1.
- **Migration scope:** config v1→v2, a real 1.9.5 data-dir copy and the exact
  1.9.3 schema fixture are covered; the SQLite schema/PII migration
  (`sito db migrate`, `SITO_DB_AUTO_MIGRATE`) and installer/container database
  upgrades are delivered. Installer/container `config.toml` auto-migration
  remains deferred. The admin API is `/api/v2` only; `/api/v1` was removed.
- Query-log anonymization is forward-only; existing rows are not rewritten.
- The 1M-row/90-day soak remains a capacity-testing residual. The
  `keep_aggregates` clear is no longer a whole-range residual: it is chunked,
  commits each chunk, and resumes safely; the sweep is still linear in the
  number of cleared rows.
- **`stats_watermark` is diagnostic (B7, accepted residual).** Retention writes
  it on every aggregated chunk for progress diagnostics and v1.9 schema
  compatibility, but no production path reads it to skip rows. The aggregate
  read, rollup upsert, watermark update and delete share one transaction per
  chunk, and backdated rows are re-aggregated on the next sweep; the
  `--keep-aggregates` clear has one documented deleted-rollup exception: if an
  hour's rollup exists when the clear reaches that hour but rollup retention
  deletes it mid-run, the clear still clears the detailed rows without
  resurrecting that rollup (a row already absent when the clear reaches its hour
  is recreated normally). A watermark-based skip is a future design change
  that needs a closed-hour and late-row reopen model. This is not a missing 2.0
  read optimization. See
  [migration §10.1](2.0-migration.md#101-backendstats-residual-b7).
- **A TTL-only live cache apply is cold by design (B8, accepted residual).** The
  runtime apply publishes the new policy and advances the policy epoch instead
  of re-clamping warm entries, so old-generation entries are unservable and the
  cache refills as queries recur; new inserts use the new TTL policy. Direct
  cache users keep the warm re-clamping `DnsCache::update_config` path. The only
  impact is a transient hit-rate drop, with no correctness issue; preserving
  warm entries is a future optimization, not a missing 2.0 feature. See
  [migration §10.2](2.0-migration.md#102-cache-ttl-residual-b8).
- HA edit-time rejection covers the API/UI apply path (`PUT /api/v2/config`,
  with a read-only Settings/System rendering on a replica). The System reload
  action is middleware-blocked only; a direct shared-field edit of
  `config.toml` that bypasses the API is detected after the write as drift and
  requires a full apply, except for `server.role`, `server.log_level`,
  `server.log_format` and the sanitizer-stripped legacy `[auth]` keys, which the
  projection excludes (`log_level` is hot-applied; the others are node-local or
  inert). An existing watermark
  written before this projection change may force one full apply after the
  upgrade. Filtering/clients/rewrites/upstreams UI pages still rely on the
  slave middleware 409 rather than a per-page read-only rendering.
- The release image scan is linux/amd64-only; per-arch scanning and root-gated
  HA ownership CI remain follow-ups. The release workflow now runs a live
  DNS/health smoke against the attested image.
- `dns.bind` still defaults to wildcard and the ACL's typed default remains
  `default_policy = "allow"` so upgrades and headless installs preserve existing
  behavior. Only a fresh wizard install starts deny; firewall/bind restriction
  remains defense in depth. HA residual: the DNS gate is unit-tested through the
  startup seam, not a full socket-level `DnsListenerManager` integration test;
  a setup-pending slave now starts its worker only after setup completion but
  still waits for the first watermarked bundle. Automatic promotion is
  implemented (opt-in, default `false`) with the witness lease, quiesce,
  reconciliation, durable fencing, status/metrics/audit and the local
  `confirm-promotion`/`clear-fence` CLI; legacy peers that cannot report
  `have_bundle_hash` make a promotion-enabled cluster report
  `promotion_peer_capability_missing` in readiness and abort reconciliation with
  `candidate_hash_unknown` instead of risking a fork. The witness is a single
  point of availability, not safety: an outage fences the current master after
  the TTL and blocks promotion until it returns (DNS reads continue).
- `chrono` (RUSTSEC-2026-0543) and `basic-toml` (RUSTSEC-2026-0374) remain
  reviewed suppressions; see the Phase 3 review for impact, reachability and the
  2027-01-31 review date.
- `allow_unpinned_tls` and `allow_insecure_ws` are explicit insecure opt-outs;
  a configured pin or CA is always enforced, and plaintext cannot be combined
  with TLS-only pins/CA (validation rejects it), enabled implicitly, or run
  without a shared token on both ends.

# 2.0 Public API Diff

This document records the public API, crate and feature changes introduced by
the Phase 1 foundation work packages, the HA consolidation and the Phase 2
core-hardening work packages (WP-2.1 through WP-2.13). Sections 1-4 describe
**WP-1.1 — Freeze/cut non-core features and dead code**; section 5 describes
**WP-1.2 — Normalized domain and client identity model**; sections 6-8 describe
**WP-1.3 — Config v2 schema and one validator**; section 9 describes **WP-1.4 —
staged runtime generation and atomic apply**; section 10 describes **WP-1.5 —
module splits**; section 11 describes **WP-1.6 — shared response shaping and
cache keys**; section 12 describes **WP-1.7 — error, health and readiness
policy**; section 13 describes **WP-1.8 — test harness, mocks, and deterministic
timing**; section 14 describes **WP-1.9 — fuzz, benchmarks and CI gates**;
section 15 describes the **HA consolidation**: the optional HA module, its `ha`
feature and the portable `sito-ha-types` contract crate. Sections 16-26 describe
the Phase 2 contracts: DNSSEC (§16), filter (§17), rewrites (§18), clients and
schedules (§19), transport admission/TLS (§20), upstream per-attempt metrics
(§21), auth/RBAC (§22), cache shaping (§23), stats/PII (§24), HA protocol v2
(§25), and API/OpenAPI/config-apply/updater hardening (§26). Section 27 records
the client-visible `/api/v2` REST contract (BC-10). `/api/v2` is the only
mounted administrative API; `/api/v1` was removed in 2.0.0.

This is the migration reference for code that depended on the 1.9.x workspace.
The operator-facing [`docs/2.0-migration.md`](2.0-migration.md) links here and
maps the stable breaking-change IDs to migration steps.

The changes are source-breaking for consumers of the internal workspace
crates. The WP-1.1/1.2 sections below do not change the `sito` binary's TOML
schema or API; WP-1.3 (sections 6-8) deliberately changes the TOML schema,
admin write semantics and CLI for 2.0.

## 1. RouterOS is now an optional crate

RouterOS DHCP lease synchronization (HTTP client, response parsing and the
background sync task) moved out of `sito-clients` into the new optional
`sito-routeros` crate. **The default `sito` build does not link it.**

| Before (1.9.5) | After (2.0) | Notes |
|---|---|---|
| `sito_clients::routeros::RouterOsConfig` | `sito_clients::RouterOsConfig` (unchanged path) | Plain serde data type only; no `reqwest`. |
| `sito_clients::RouterOsError` | `sito_routeros::RouterOsError` | Moved; adds `MissingTokenEnv` for a configured but unresolvable `token_env` (no basic-auth fallback). |
| `sito_clients::fetch_routeros_leases` | `sito_routeros::fetch_routeros_leases(config)` | Moved and narrowed: the client is built from the config, so an arbitrary insecure client can no longer receive identity-capable leases. The raw-client path is private to the crate (sync task and tests). |
| `sito_clients::spawn_routeros_sync` | `sito_routeros::spawn_routeros_sync` | Moved. |
| `sito_clients::routeros::{RawRouterOsLease, ROUTEROS_REQUEST_TIMEOUT, build_routeros_client}` | `sito_routeros::{RawRouterOsLease, ROUTEROS_REQUEST_TIMEOUT, build_routeros_client}` | Moved. `RawRouterOsLease::into_lease` now takes `verified: bool`. The type remains public for in-process parsing; only the fetch/sync path proves the peer, so direct constructors must set `verified` deliberately. |
| `sito_clients::RouterOsLease` | `sito_clients::RouterOsLease` (same path) | Registry matching stays in `sito-clients`; the struct gains `verified: bool`, true only for `https://` with certificate verification. Unverified leases are display-only and never identify clients. |
| `sito_clients` dependency `reqwest` | removed | The default build no longer links the RouterOS HTTP stack. |

### Build and feature changes

```toml
# crates/sito/Cargo.toml
[features]
routeros = ["dep:sito-routeros", "sito-api/routeros"]
```

| Crate | Feature | Effect |
|---|---|---|
| `sito` | `routeros` | Adds `dep:sito-routeros` and forwards `sito-api/routeros`. Not in `default`. |
| `sito-api` | `routeros` | Internal capability flag: configuration validation accepts an enabled `[integrations.mikrotik]`. It does not add a dependency. |

The optional crate honours the D15 security bar: environment proxies are
disabled (`.no_proxy()`), error bodies are capped at 4 KiB, a configured but
unresolvable `token_env` is an error rather than a basic-auth fallback, and a
lease is identity-capable (`verified = true`) only when **both** conditions
hold: the `url` uses `https://` and `allow_invalid_certs = false`. A plaintext
`http://` URL (even with `allow_invalid_certs = false`) and an insecure-TLS
client both produce `verified = false`; such leases are display-only and the
registry never grants a group/trusted/MAC identity from them. The sync task
logs an explicit warning for either case, and `enabled = true` with a scheme
other than `http://`/`https://` is rejected by config validation.

```bash
cargo build -p sito                       # default: no sito-routeros
cargo build -p sito --features routeros   # optional integration included
```

`cargo tree -p sito --locked` must not contain `sito-routeros`;
`cargo tree -p sito --features routeros --locked` must contain it. The
integration remains **experimental**.

The default binary still links `reqwest` for unrelated features (ACME
HTTP-01/TLS-ALPN and the self-updater); the RouterOS-specific proof is the
absence of the `sito-routeros` crate and the rejection of an enabled
`[integrations.mikrotik]`.

A build without the feature rejects `[integrations.mikrotik] enabled = true`
during startup, `check-config` and API writes with an error naming the
`routeros` feature. It is never silently ignored. A disabled section is still
accepted in every build.

## 4. Non-Unix fallbacks

`sito-transport` already refuses non-Unix targets with `compile_error!` in
`lib.rs`, `udp.rs` and `pktinfo.rs`. The unreachable `#[cfg(not(unix))]`
permission fallbacks in `acme.rs` and the redundant `#[cfg(unix)]` gates were
deleted; Unix-only code is now unconditional inside the crate. Windows remains
unsupported.

## 5. WP-1.2 — Normalized domain and client identity model

WP-1.2 introduces canonical domain/network primitives in `sito-core` and moves
client policy onto an explicit identity-with-provenance model. It addresses
P1-9, P2-97..P2-99 and the IDN gaps.

### 5.1 New `sito-core::domain` API

```rust
pub struct NormalizedDomain(/* lowercase ASCII/punycode */);

impl NormalizedDomain {
    pub fn parse(raw: &str) -> Result<Self, DomainError>;      // IDN + wildcard + root
    pub fn parse_ascii(raw: &str) -> Result<Self, DomainError>; // historical wire form
    pub fn parse_idna(raw: &str) -> Result<Self, DomainError>;  // wire form with IDN
    pub fn root() -> Self;
    pub fn as_str(&self) -> &str;
    pub fn is_root(&self) -> bool;
    pub fn has_wildcard_labels(&self) -> bool;
    pub fn matches_suffix(&self, suffix: &Self) -> bool;
    pub fn is_strict_subdomain_of(&self, suffix: &Self) -> bool;
    pub fn into_string(self) -> String;
}
```

`NormalizedDomain` implements `Display`, `FromStr`, `TryFrom<&str>`,
`TryFrom<String>`, `Serialize` and `Deserialize`. Deserialization normalizes
(therefore `"EXAMPLE.COM."` becomes `"example.com"`), and serialization always
emits the canonical form.

`parse` converts raw Unicode/IDN labels to punycode, lowercases ASCII, strips
one trailing dot, validates label (63-byte) and name (253-byte) limits, keeps
wildcard labels (`*`, `*.example.com`, `*.banner.*`), and represents the root
as `"."`. `parse_ascii` and `parse_idna` preserve the historical wire contract:
raw Unicode, wildcards and the root are rejected where they were rejected
before. `DomainError` mirrors the former `ProtoError` normalization variants.

`sito_proto::normalize_domain` and `normalize_domain_or_idna` now delegate to
these constructors and map `DomainError` back to `ProtoError`, so their public
signatures and error type are unchanged.

### 5.2 New `sito-core::net` API

```rust
pub struct IpNetwork { /* address + prefix */ }

impl IpNetwork {
    pub fn new(addr: IpAddr, prefix: u8) -> Result<Self, CidrError>;
    pub fn parse(value: &str) -> Result<Self, CidrError>;
    pub fn addr(&self) -> IpAddr;
    pub fn prefix(&self) -> u8;
    pub fn contains(&self, target: IpAddr) -> bool;
    pub fn network_address(&self) -> IpAddr;
}

pub fn ip_in_subnet(network: IpAddr, prefix: u8, target: IpAddr) -> bool;
```

`IpNetwork` implements `Display`, `FromStr` and `Hash`. `CidrError` rejects
missing/extra separators, unparsable addresses and prefixes larger than 32
(IPv4) or 128 (IPv6). Membership tests always mask host bits and never match
across address families.

### 5.3 New `sito-core::client` API and `ClientContext` migration

```rust
pub enum IdentitySource {
    Ip, Cidr, Mac, TlsSni, DohPath, Secret, RouterOs,
}

pub struct ClientIdentity {
    pub ip: IpAddr,
    pub source: IdentitySource,
    pub authenticated: bool,
    pub name: Option<String>,
    pub group: Option<String>,
    pub mac: Option<String>,
}

impl ClientIdentity {
    pub fn from_context(ctx: &ClientContext) -> Option<Self>;
    pub fn may_match_secret_rules(&self) -> bool;
    pub fn may_match_client_exception(&self) -> bool;
}
```

`IdentitySource::is_trusted` follows D10: `Ip`, `Cidr`, `Mac`, `Secret` and
verified `RouterOs` are identity-capable; `TlsSni` and `DohPath` are
display/statistics-only. The two `may_match_*` methods are true only when the
identity is both authenticated and from a trusted source. The serde name of
every variant matches `IdentitySource::as_str()` (including `routeros`).

`ClientIdentityRef<'a>` is the borrowed form used on hot paths; it exposes
`ip`, `source`, `authenticated`, `name: Option<&str>`, `group` and `mac`, plus
the same `may_match_*` methods. `ClientContext::identity_ref()` returns it
without cloning strings.

`ClientContext` gains:

| Field / method | Change | Notes |
|---|---|---|
| `identity_source: Option<IdentitySource>` | new, `#[serde(default, skip_serializing_if = "Option::is_none")]` | Older serialized contexts deserialize with `None`. |
| `identity_ref()` / `identity()` | new | Borrowed and owned policy identities. Legacy in-process contexts that only populated `client_name`/`group` are treated as an authenticated IP identity; registry-produced contexts always carry an explicit source. |
| `may_match_secret_rules()` / `may_match_client_exception()` | new | Convenience wrappers over `identity_ref()`. |
| `ClientContext::with_id` | behaviour | Records `IdentitySource::DohPath`, unauthenticated. |
| `ClientContext::with_sni` | behaviour | Records `IdentitySource::TlsSni`, unauthenticated. |
| `ClientContext::with_authenticated_id` | behaviour | Records `IdentitySource::Secret` in addition to `id_authenticated = true`. |

`ClientRegistry::resolve` now records the matching source: exact IP (`Ip`),
CIDR (`Cidr`), ARP MAC configured on an entry (`Mac`), verified RouterOS lease
(`RouterOs`), configured secret (`Secret`), and otherwise the untrusted
wire-claimed `TlsSni`/`DohPath` label. A trusted RouterOS lease hostname copied
into `client_name` keeps `RouterOs` provenance. An unverified RouterOS lease
still never grants identity (WP-1.1 rule preserved).

`clients.trust_arp` (optional, default `false`) extends the ARP `Mac` case: when
enabled, an ARP-resolved MAC is a trusted `IdentitySource::Mac` identity even
when no entry lists that MAC, so `$client` MAC rules and rewrite
`exception_clients` can match it. The opt-in is **MAC-only** — ARP hostnames and
every other ARP attribute remain untrusted, and no client name/group is invented
from the MAC alone. With the setting off (the default), an unlisted ARP MAC is
display-only (`identity_source = None`). Exact IP/CIDR, configured secrets and
verified RouterOS leases keep their precedence; an ARP MAC never downgrades an
already trusted identity, and when an IP/CIDR/secret entry matches, the MAC is
still recorded for display and MAC matchers.

### 5.4 Policy now uses identity, never `ctx.id`

| Crate | Change | Migration |
|---|---|---|
| `sito-filter` | `$client` name/group/MAC matching requires `ClientIdentity::may_match_client_exception()`. | Wire-claimed DoH path/SNI labels never satisfy `$client`; IP/CIDR matchers still use the query source address. |
| `sito-rewrites` | `exception_clients` matches only an authenticated identity's name/group/MAC, or an IP/CIDR. | A raw `ClientContext::id` (even a registry-authenticated secret) no longer satisfies an exception; match the resolved client name/group/MAC instead. |

The `ctx.id` audit found no remaining policy use. `sito-clients` still consumes
`ctx.id` during identification (it is the credential being matched) and
transport/stats/tests use it for display only.

# WP-1.3 — Config v2 schema and one validator

Section 6 describes the config v2 freeze. The user-facing contract changes are
breaking for 2.0 (Phase 1 may break config/API contracts per the release
mapping); source consumers of the internal crates should follow the table.

## 6. Config schema and defaults

| Before (1.9.x / WP-1.2) | After (2.0) | Migration |
|---|---|---|
| `config_version` default `1`; only `1` accepted | default `2`; only `2` accepted | Run `sito config migrate --from v1 --to v2 --backup`. A v1 document is rejected with that command in the error. |
| Unknown TOML keys/tables silently ignored | Rejected at parse time (typed `deny_unknown_fields` + map walk for legacy raw sections) | Remove the key, or use `--ignore-unknown-keys` **only** during migration. |
| `[web] bind` default `"0.0.0.0"` | `"127.0.0.1"` | Migrated v1 files keep `0.0.0.0`; pass `--adopt-safe-defaults` to opt into loopback. New installs get loopback. |
| `[dns.tls]` preferred over `[tls]` | Typed `[tls]` is canonical; `[dns.tls]` remains a deprecated alias for one alpha | `sito config migrate` moves it to `[tls]`. |
| `[web] acme_*` legacy keys | Typed `[acme]` canonical; `[web] acme_*` deprecated for one alpha | `sito config migrate` moves them to `[acme]`. |
| `stats.query_log_retention_days`, `privacy.anonymize_client_ip` aliases | Still accepted; canonical keys are `stats.retention_days` and `privacy.anonymize_querylog` | `sito config migrate` rewrites them. |
| `auth.admin_password_hash`, `auth.tokens`, `integrations.mikrotik.token` tolerated | Removed: rejected by the v2 parser | Migration drops and reports them. Sessions/tokens live in `data_dir` stores. |
| Duplicate `dns.bind`, web/DNS port collisions, empty `server.data_dir`, bad upstream targets, invalid ACME domains, bad `[integrations.lists]` accepted until later runtime failure | Rejected by `Config::validate_full()` | Fix the value; the error names the dotted field. |

The schema is frozen here. Any later field must be optional with a default or
land in a v2.1 migration. `clients.trust_arp` landed after the freeze as such an
optional field (`false` by default; see §5.3); enabling it is an explicit opt-in,
not a migration.

# WP-1.4 — Staged runtime generation and atomic apply

There are no TOML schema or REST contract changes in WP-1.4. The changes are
source-level for embedders that published runtime components directly; the
admin API, HA push, restore and file watcher now share one staged apply and
publish exactly one runtime generation.

`sito_proto::ResponseShaper`. The envelope is derived exclusively from the
current client query; the cached/upstream/local message is treated as data.
`docs/audit6-test-matrix.md` maps the WP-1.6 tests.

### `sito-core`

| Item | Change | Migration |

| Item | Change | Migration |

| `DnsCache::insert_validation_failure_at_epochs` | new | Stores a strict-mode Bogus SERVFAIL with empty answer/authority/additional sections and empty TTL vectors. ### Behavior notes

- A non-EDNS client never receives an OPT record; an EDNS client receives a
  fresh OPT with the resolver payload size, the client's DO bit and (if
  present) the RFC 8914 EDE diagnostic only.
- CD=1 responses never assert AD and never share a cache entry with CD=0 (the
  key already separated them; the shaper now keeps the flag coherent).
- `TC` is preserved by the shaper; response size/truncation remains owned by
  the transport/framing layer (WP-1.6 does not change P1-14 behavior).
- A reload advances the runtime/cache generation as in WP-1.4; the TTL
  re-clamp additionally makes the cache API correct when called directly or if
  a future generation policy keeps entries alive across a cache-only reload.

## 12. WP-1.7 — error, health and readiness policy

### `/health` is now a generic probe (breaking response shape)

| Before (1.9.x) | After (2.0) |
|---|---|
| Always `200` with `{status, setup_pending, ha:{required,ready,reason}, acme:{enabled,ready,reason}}` | `200 {"status":"ok"}` when ready; `503 {"status":"unavailable"}` when not |

The endpoint no longer exposes component names, reason codes, error strings,
filesystem paths, setup state or configuration values. Consumers that parsed
`setup_pending`/`ha`/`acme` from `/health` must use the admin API:
`GET /api/v2/status` (Viewer) carries `ready` and `reasons[]`, and
`GET /api/v2/ha/status` carries the detailed HA reason. The `sito healthcheck`
subcommand now treats a `503` (or a body without `status: ok`) as not ready and
uses the existing setup-pending middleware signal (`/api/v2/status` → `503
Setup not completed`) instead of a `setup_pending` field. It probes `/health`
whenever the admin listener answers, not only on HA nodes. `/health` does not
run the advisory stats database probe; `/status` does, bounded to 750 ms.


### `GET /api/v2/status`

Additive. The existing `version`, `uptime_seconds`, `role`, `listeners` and
`acme` fields are unchanged.

| Field | Type | Notes |
|---|---|---|
| `ready` | `bool` | Same aggregate verdict as `/health`. |
| `reasons` | `ReadinessReason[]` | Component/code/message/since, in component order. |
| `ReadinessReason.component` | `string` | `listeners`, `tls`, `acme`, `ha`, `filter`, `stats`. |
| `ReadinessReason.code` | `string` | Stable machine-readable code (for example `listener_bind_failed`). |
| `ReadinessReason.message` | `string` | Human summary; never contains secrets or certificate text. |
| `ReadinessReason.since_unix_ms` | `u64?` | Omitted when the failure start time is unknown. |

A stats database/writer outage is reported as `stats_unavailable` but does not
set `ready` to false. A retained filter snapshot (`FilterState::Failed` or
`Loading` with `unavailable == false`) is `filter_degraded`, also non-blocking;
only `unavailable == true` is not-ready. The D12 certificate ladder reports a
renewal failure or a certificate expiring within 30 days as degraded and an
expired certificate as not-ready. See `docs/runbook-ha.md` for the full
component matrix.

## 16. Phase 2 — DNSSEC validation

Phase 2 bounds every DNSSEC key fetch with one absolute per-query deadline and
one shared count budget, pins denial handling to RFC 6840/5155, and exports
validation outcomes and fetch refusals as metrics. No new breaking-change ID is
introduced: BC-6 already covers internal workspace Rust API changes, and the
only source-breaking item here is the `DnssecKeyFetcher` trait signature.

### 16.1 Deadline-aware `DnssecKeyFetcher`

`sito_core::DnssecKeyFetcher::query` now takes the absolute deadline shared by
every fetch made for one client query:

| Before (1.9.x / Phase 1) | After (2.0 Phase 2) |
|---|---|
| `async fn query(&self, name: &Name, rtype: RecordType) -> Result<Message, UpstreamError>` | `async fn query(&self, name: &Name, rtype: RecordType, deadline: Instant) -> Result<Message, UpstreamError>` |

Every implementor must accept the parameter and must not wait past it. A stalled
upstream or a black-holed DS/DNSKEY lookup must return `UpstreamError::Timeout`
rather than ignoring the argument and relying on an outer timeout.
`sito_upstream::UpstreamKeyFetcher` implements this with
`tokio::time::timeout_at`. The resolver pipeline retains an outer `timeout_at`
as a final guard for third-party fetchers that ignore the argument.

This is the one source-breaking change in this section: an implementation that
keeps the old two-argument signature no longer compiles. Call sites do not
change unless they call the trait directly.

### 16.2 `FetchBudget` and deadline constants

`sito_dnssec::FetchBudget` is the per-query fetch permit. Both limits are
enforced together, and a refusal is attributed to exactly one cause (the
absolute deadline takes precedence over count exhaustion).

| Item | Meaning |
|---|---|
| `FetchBudget::new(remaining: u8, deadline: Instant)` | At most `remaining` fetches before `deadline`. |
| `FetchBudget::with_metrics(remaining, deadline, metrics)` | Same, recording each refusal in `DnssecMetrics`. |
| `deadline() -> Instant` | The absolute deadline every fetch must respect. |
| `try_take() -> bool` | Consumes one slot; `false` means stop fetching. |
| `is_expired() -> bool` | Whether the absolute deadline has passed. |

`sito_dnssec::DEFAULT_KEY_FETCH_DEADLINE` is five seconds. It is applied only by
the source-compatible `validate_with_key_fetcher` wrapper; the resolver
pipeline passes its own absolute deadline and keeps `DNSSEC_VALIDATION_DEADLINE`
in `crates/sito/src/pipeline/query.rs` in sync with this value.

Refusals at the walk/probe entry `is_expired()` guards are recorded with the
same deadline cause as a `try_take` refusal, so an already-expired budget is
visible as `kind="deadline"` even when no fetch is attempted. An upstream
`UpstreamError::Timeout` is a fetcher result, not a budget refusal, and is
covered by the separate upstream/bogus error metrics rather than these counters.

Three crate-internal constants define the count bound and are deliberately not
exported:

- `MAX_CNAME_PROBES = 8` caps the CNAME/delegation probes per query.
- `MAX_SIGNER_CHAIN_FETCHES = 31` is the old cold-start allowance for one RRSIG
  signer (`labels * 2 + 1`, capped at 31), so a single signer walk can never
  need more.
- `MAX_FETCHES_PER_QUERY = 47` is `MAX_SIGNER_CHAIN_FETCHES + 2 *
  MAX_CNAME_PROBES` (`31 + 2 * 8`). The second term is the worst-case probe
  share: one anchor DNSKEY plus one DS lookup per probe. It is a single hard
  cap, not a reservation: deep probes also draw from the signer share, so 47
  guarantees the query never exceeds 47, not that every cold-start walk still
  has 31 fetches after a deep probe fan-out.

All early probes, every cold-start signer walk and the post-fetch probes draw
from the same `FetchBudget`. A probe fan-out therefore leaves only the
remainder for the cold-start walk instead of multiplying the query's total
fetch work.

### 16.3 `TrustChainState`, `ValidationDecision` and deadline validation

`sito_dnssec::TrustChainState { Signed, Unsigned, Unknown, Bogus }` is the
outcome-free classification of a zone's chain. It has no NTA variant: a bypass
is a policy decision, not a chain state.

`sito_dnssec::ValidationDecision { Secure, Insecure, Bogus { reason, ede_code },
Indeterminate }` is the planned decision type for the `TrustChain` refactor.
The validator still returns `ValidationOutcome` today; `ValidationDecision` is
additive and is derived from an outcome or a chain state until call sites
migrate. `ValidationOutcome` remains the wire and metrics type.

| `TrustChainState` | `ValidationDecision` |
|---|---|
| `Signed` | `Secure` |
| `Unsigned` | `Insecure` |
| `Unknown` | `Indeterminate` |
| `Bogus` | `Bogus { reason: "trust chain is bogus", ede_code: EDE_DNSSEC_BOGUS }` |

Conversions are available as `ValidationDecision::from_outcome` and
`to_outcome`, plus `From<TrustChainState> for ValidationDecision` and
`From<ValidationDecision> for ValidationOutcome`. `ValidationOutcome::NtaBypass`
folds into `Insecure` because both are AD=0; that is the only lossy mapping, so
not every mapped outcome round-trips. The NTA distinction is kept by the public
`DnssecMetrics::nta_bypass_total`, not exported as a Prometheus family. Bogus
reasons and EDE codes are preserved.

`DnssecValidator::validate_with_key_fetcher_deadline(response, upstream, now,
fetcher, deadline)` is the new entry point for callers that already own a
per-query deadline. The older `validate_with_key_fetcher(response, upstream,
now, fetcher)` remains and applies `DEFAULT_KEY_FETCH_DEADLINE`; existing
callers do not need to change.

### 16.4 Metrics

Phase 2 adds two counter families to the Prometheus exposition:

| Metric | Labels | Meaning |
|---|---|---|
| `sito_dnssec_validations_total` | `result="secure"`, `"insecure"`, `"bogus"`, `"indeterminate"` | Validation outcomes. NTA bypasses are not a label here; they are tracked only by the public `DnssecMetrics::nta_bypass_total` field, not exported as a Prometheus family. |
| `sito_dnssec_fetch_failures_total` | `kind="budget"`, `"deadline"` | DS/DNSKEY fetches refused by the shared count budget or the absolute deadline. |

The counters are cumulative in the validator and are published after both
foreground and background validation. The background refresh path copies the
same absolute counter snapshots
(`crates/sito/src/pipeline/stages.rs:645-655`). The metrics registry setters
replace the exported values instead of adding to them, so a background pass
refreshes the foreground's numbers and does not double count.
`sito_dnssec_bogus_total` is unchanged.

These families are **per-validator absolute snapshots**, not process-global
totals. A DNSSEC policy reload builds a new validator whose counters start at
zero, and a validation that began under the old generation can finish late and
publish an older (lower) snapshot after the new validator has published. The
setters replace values, and Prometheus interprets a decrease as a counter
reset.

### 16.5 Behavior notes

- **Shared budget.** One `FetchBudget` covers every DS/DNSKEY lookup for a
  client query: early CNAME and delegation probes, every cold-start signer walk
  and post-fetch probes. The budget spans all probe and signer walks for the
  response, not one chain walk, so a single signer with early probes can see a
  shorter walk. When the budget or deadline is exhausted, validation stops
  fetching and fails closed instead of issuing more network I/O.
- **Signed QTYPE=CNAME/DNAME and strict Indeterminate.** Positive `QTYPE=CNAME`
  answers are validated as answer data, not treated as a negative response: a
  correctly signed QTYPE=CNAME answer is Secure/AD=1. A *stripped* signature on
  a signed QTYPE=CNAME answer (as on any signed CNAME, including intermediate
  hops) is Bogus: strict `Validate` mode turns that into SERVFAIL, while
  `LogOnly` keeps the data with AD=0. Unknown DNAME rdata remains Bogus. When
  validation ends `Indeterminate` after fetches, strict mode returns SERVFAIL;
  only log-only mode returns the data with AD=0.
- **RFC 6840 delegation locks.** A parent-side NSEC/NSEC3 at a delegation point
  (NS set, SOA clear) cannot prove NXDOMAIN for a name below the cut. At the
  delegation itself it can authenticate only the absence of DS
  (RFC 6840 §4.1/§4.4). Only the parent-zone signature authenticates a DS
  RRset: a valid signature from the DS owner itself or from a sibling/other
  zone leaves the delegation status unknown.
- **RFC 5155 NSEC3 locks.** An NXDOMAIN proof requires an exact-match closest
  encloser, a covering next-closer record and a covering wildcard record. Only
  when the closest encloser is the zone apex must its NSEC3 carry the SOA bit;
  the Phase 2 apex fix rejects an apex closest-encloser bitmap without SOA that
  previously completed a proof.
- **Bogus and Indeterminate caching.** In strict `Validate` mode a Bogus
  answer becomes a SERVFAIL with no answer data and is cached as
  `ValidationStatus::Bogus` for `DNSSEC_BOGUS_CACHE_TTL` (5 s); a repeated
  query within that window is answered from the cache without an upstream call.
  The fail-closed SERVFAIL may be served to a validating client but is never
  reused from the RFC 8767 stale path while local validation is active. In `LogOnly` the answer is kept with
  AD=0 and cached as an unservable `ValidationStatus::Indeterminate` entry,
  whose lifespan and record TTLs are capped at
  `DNSSEC_INDETERMINATE_CACHE_TTL` (30 s); it is never served to a validating
  (CD=0) client. `Secure`/`Insecure` answers may be cached; RFC 8767 stale
  answers are served only for those authenticated decisions, always with AD=0.
  A stale `Bogus`, `Indeterminate` or `Unchecked` entry is never served to a
  CD=0 client while local validation is active.
- **Background prefetch parity.** A strict Bogus encountered during a
  background refresh is cached through the same fail-closed helper as the
  foreground path: a 5 s SERVFAIL with empty answer/authority/additional
  sections, EDNS/EDE preserved, and no AD. LogOnly keeps the answer as an
  unservable `Indeterminate` entry and never writes a `Bogus` entry.
- **Defensive failure-cache gates.** The dedicated failure insert rejects a
  response that asserts AD. The status-less stale getters hide `Bogus` and
  `Indeterminate`; callers that need the status use
  `get_stale_for_query_with_status`. A fresh read also clamps an old failure
  entry's raw record TTLs to its status window, covering entries copied from
  pre-fix versions.

| `sito_core::config::MAX_REFRESH_HOURS` | new public constant `8760` (one year) | `FilteringConfig::validate` rejects `filtering.refresh_interval_hours` and `filtering.lists[].refresh_hours` above it, naming the exact field. `Config::validate_full` applies the same cap to `integrations.lists.refresh_hours` and each per-category override; the typed `ListCategoriesConfig::validate` mirrors it. Scheduling clamps to the same bound and uses checked time arithmetic, so `u64::MAX` hours cannot overflow `Instant + Duration`. |

**Behavior notes.**

- A URL change quarantines both the cached list body and its metadata before
  the fetch, so after a successful quarantine a `304` or a failed request
  cannot return the old URL's content. Legacy metadata without a URL takes the
  same path.
- The global `refresh_interval_hours` default remains 24 hours and a per-list
  `refresh_hours` of 1 behaves as before; only values above the one-year cap
  are newly rejected (or clamped at runtime for an already-loaded config).
- The verified disk-cache reader checks the metadata URL before reading the
  body, so the HTTP `304` path cannot return content without provenance even if
  a quarantine removal failed. `load_cache_or` still returns the original fetch
  error on a mismatch.
- Refresh deadlines are representable-only (`Option<Instant>`): an
  unrepresentable deadline skips the list instead of storing a past deadline or
  spinning. Per-list and global hours are resolved by one helper in both the
  initial schedule and the post-refresh reschedule.
- `[integrations.lists].refresh_hours` and each per-category override share
  `MAX_REFRESH_HOURS`; `Config::validate_full` and the typed
  `ListCategoriesConfig::validate` both enforce it, and the runtime scheduler
  clamps and uses `checked_add`.
- The `sito-cache` `test-hooks` feature exposes cross-crate test accessors only.
  It is not enabled by default, and the release workflow and Dockerfile are
  checked to never enable it.

## 18. Phase 2 — rewrites (WP-2.4)

The local rewrite table now reports a three-way outcome and validates entries at
every configuration and API entry point. `[rewrites]` values, precedence and
the stage order are unchanged.

| Item | Change | Guidance |
|---|---|---|
| `sito_rewrites::RewriteLookup` | new `Answered(Vec<Record>)` / `NoData` / `NotFound` enum; `RewriteTable::lookup` returns it instead of `Option<Vec<Record>>` | Treat `Answered` as synthesize, `NoData` as an authoritative NOERROR/NODATA answer, and `NotFound` as fall-through. An exact or wildcard `A`/`AAAA`/`PTR`/`TXT` owner answers NODATA for an unconfigured qtype with zero upstream queries. A `CNAME` owner returns the CNAME chain as `Answered` (a target that is not in the table still answers with the CNAME itself); a chain that can produce no record, such as a self-referential or otherwise unproductive cycle, returns `NotFound` and falls through. Auto-PTR owners answer `PTR` and return NODATA for other types. An `exception_clients` match or an unknown name returns `NotFound` and falls through to normal resolution. |
| `sito_rewrites::txt_chunks` | new public 255-byte, UTF-8-safe TXT chunker; an empty value yields one empty string | The pipeline and local rewrites share this chunker, so multi-byte UTF-8 values split on character boundaries and multi-chunk TXT values encode/decode as valid DNS character-strings. |
| `RewriteEntryConfig::validate` / `RewritesConfig::validate` | new validation; `validate_typed_sections` and `check-config` call it, and `POST`/`PUT /api/v2/rewrites` return `400` `ProblemDetails` before persisting | Rejects an invalid exact/wildcard domain (including nested wildcards), an unsupported type outside A/AAAA/CNAME/PTR/TXT, an unparsable or empty answer (whitespace-only TXT is allowed; TXT over 65,535 bytes is not), and an invalid `exception_clients` value. An invalid programmatic entry is logged and skipped by `RewriteTable::new`. |
| Safe search | `apply_safe_search_rewrite` returns no rewrite unless the question type is `A`, `AAAA` or `HTTPS` | `MX`, `TXT`, `CNAME` and other qtypes resolve normally instead of receiving a synthesized safe-search CNAME. |

**Behavior notes.**

- An exact or wildcard `A`/`AAAA`/`PTR`/`TXT` owner is authoritative: an
  `A`-only owner queried as `AAAA`, `TXT`, `PTR` or `HTTPS` returns
  NOERROR/NODATA without an upstream query. `ANY` at such an owner is NODATA by
  design. The exception-client bypass is checked first, so an excepted client
  still falls through to upstream. Stage 2 (local rewrites) runs before
  standard, parental and service blocking, so those block stages do not apply
  to locally owned qtypes.
- A `CNAME` owner answers with its CNAME chain for any qtype, including a
  CNAME to a target outside the table. A chain that can produce no record
  (for example a self-referential or otherwise unproductive cycle) returns
  `NotFound` and falls through to normal resolution instead of synthesizing
  NODATA. Auto-PTR owners answer `PTR` and return NODATA for other types.
- Startup/config load, `sito check-config`, config restore/HA apply and the
  admin API all call `validate_typed_sections`, which uses the same
  `RewritesConfig::validate` implementation, so invalid entries are rejected
  before they can be persisted as inert configuration. Validation is also
  applied when a `RewriteTable` is built programmatically: invalid entries are
  logged at `warn` and skipped.
- TXT chunking never splits a UTF-8 code point; a value over 255 bytes becomes
  multiple character-strings in one TXT record.

Cache helpers now distinguish the shaped, status-less read path from the raw

| Response caching | every `/api/v2/` operation plus `/metrics` and `/ui/` returns `Cache-Control: no-store` and `Vary: Cookie` | Shared caches must not serve one caller's authenticated response to another. |
| Querylog WebSocket | `GET /api/v2/querylog/stream` rejects cross-origin and `Origin: null` upgrades; a session-authenticated browser request must send a same-origin `Origin`; token clients may omit it | Use a browser-origin URL with the session cookie, or an `Authorization: Bearer` token. The legacy `?token=` query parameter is removed by BC-8 (WP-2.14); do not put credentials in the URL. |
| Viewer filtering page | configured list URLs, runtime/integration `source_url` values and URLs embedded in refresh errors are reduced to scheme+host for roles below Operator | Operators still see the full source; Viewers still see the source host so they can identify the category. |

### 26.2 Config apply, references and backups

| Item | Change | Guidance |
|---|---|---|
| Admin config apply | unrelated cache/DNSSEC/upstream changes use a deferred filter apply and succeed while a blocklist source is unavailable; any `[filtering]` change stays synchronous | A deferred apply never publishes changed filtering rules. |
| Restart-only writes | `PUT /api/v2/config` and restore return `409` with `restart_required` and persist nothing when a restart-only field changes. `POST /api/v2/config/reload` returns `200` with `restart_required` because the on-disk file is already authoritative; the restart-only value is not applied live | Edit `config.toml` and restart, or use the installer. |
| References | `clients.groups.*.lists` must name a configured `filtering.lists` entry; renaming/deleting a referenced filter list or deleting a referenced client group returns `409` and changes nothing | Update the group/list references first. |
| Rewrites | invalid rewrite entries return `400` instead of being persisted and skipped | Invalid rows are never written. |
| Backup/config reads | `GET /api/v2/config` and `GET /api/v2/config/backup` return `500` if the config file cannot be read; backup `config.toml` is mode `0600`; restore rejects unknown `BackupMetadata.version` | A backup is never synthesized from in-memory defaults, and future metadata formats are refused rather than misread. |

### 26.3 Updater behavior

| Item | Change | Guidance |
|---|---|---|
| Managed environments | in-app apply is disabled when running under systemd (`INVOCATION_ID`/`JOURNAL_STREAM`) or Docker and returns `409`/`400` with instructions; `--check` still works | Stop the service, run `sudo sito update`, then start it. Docker upgrades use image pulls. |
| Version truth | `version_comparison_unknown` is surfaced in `UpdateInfo`; the UI, CLI and apply path never report “up to date” for an unknown comparison, and apply requires `force` | Use `sito update --force` only when an explicit reinstall is intended. |
| Apply safety | one process-wide update lock (concurrent applies get `UpdateInProgress`/`409`); downloaded assets are `0600`; the staged binary is verified with `--version`; the old binary is backed up and restored on failure | The lock is process-wide; a separate CLI process is not serialized against the server. |
| Signatures | a present `.sig`/`.pem` pair is always verified, even when `update_require_signature = false`; present signatures without a verifier fail; incomplete pairs fail; only “no signature assets + optional” may skip verification | Install cosign or remove the assets from the release; do not rely on optional mode to ignore a present signature. |

### 26.4 Status-code changes

- `POST /api/v2/clients`, `/clients/groups`, `/filtering/lists` and `/rewrites`
  return `201 Created`; duplicate groups remain `409`.
- Restart-only config writes/restores and reference conflicts return `409`;
  invalid references/rewrites return `400`.
- The updater returns `409` for an in-progress apply, systemd-managed apply or
  unknown version that needs `force`; Docker remains `400`.

## 27. Client-visible REST contract (BC-10)

This is the exact HTTP contract for 2.0 clients. It records the client-visible
result of the v1 removal, query-log cursor pagination, the upstream alias and the
auth/status hardening. Source-level Rust changes stay in §2 and §22; the
WebSocket credential rule is BC-8 (§26.1). The operational checklist and
copy-paste examples are in
[migration §5.4](2.0-migration.md#54-client-visible-rest-contract-bc-10).

### 27.1 API surface and credentials

| Item | Contract |
|---|---|
| Base path | `/api/v2` is the only mounted administrative API. Once setup is complete, `/api/v1` and every `/api/v1/...` path return `404` with a `ProblemDetails` JSON body. There is no v1 alias, redirect or compatibility facade. |
| Login | `POST /api/v2/auth/login` body `{"user":"admin","pass":"..."}`. Success is `200 {"username":"admin","role":"admin","totp_required":false}`. The session is delivered only as an `HttpOnly` cookie, never in the JSON body. |
| Session cookie | Secure request (TLS or a trusted TLS-terminating proxy): `__Host-sito_session`; plain HTTP: `sito_session`. The server accepts both names, but the client sends back the one it received. Attributes: `HttpOnly; SameSite=Strict; Path=/` plus `Secure` on TLS. |
| CSRF | `sito_csrf` is a non-HttpOnly double-submit cookie. Cookie-authenticated mutating requests must send `X-CSRF-Token` with the same value (or `csrf_token` as a form field) **and** a same-origin `Origin` (same-origin `Referer` is the fallback); a cookie session with neither fails closed. Bearer requests are exempt and may omit both. |
| TOTP | A TOTP-enrolled login returns `202` with `totp_required:true`; the short-lived partial token is the `HttpOnly` `sito_partial` cookie, or the `partial_token` body field when the request sends `X-Sito-Token-Delivery: body`. Complete with `POST /api/v2/auth/totp/verify` body `{"partial_token":"...","code":"..."}`. |
| Bearer token | Send `Authorization: Bearer sito_...`. Mint a token (Admin only) with `POST /api/v2/auth/tokens` body `{"name":"...","scope":"viewer"}`; the response is `201 {"id":"tok_...","name":"...","scope":"viewer","token":"sito_..."}` and `token` is shown once. |
| Re-authentication | `POST /api/v2/auth/reauth` body `{"password":"...","code":"..."}` (code required when TOTP is enabled) returns `200 {"reauth_token":"...","expires_in":300}`. Send the ticket as `X-Reauth-Token` on sensitive session mutations. It is single-use, session-bound and expires after 300 seconds. Missing/expired/used/wrong-session ticket: `401`. An API-token caller attempting re-authentication: `403`. |
| Sensitive mutations | Role changes, Admin overrides, Admin creation, Admin-scoped token creation, user deletion, token revocation and TOTP enrollment/disable require `X-Reauth-Token` for session callers. API-token callers are exempt, except TOTP management and password changes, which API tokens cannot perform. |
| Query string | Session and bearer credentials are not read from the query string. `/api/v2/querylog/stream` rejects the removed `?token=` form; use the cookie or Bearer header. Browser session upgrades must send a same-origin `Origin`; `Origin: null` and cross-origin upgrades are `403`. |

### 27.2 `GET /api/v2/querylog`

Permission: **Viewer** or higher.

Request parameters (query string):

| Name | Type | Contract |
|---|---|---|
| `client` | string | Exact match on `client_ip` **or** `client_name`. |
| `domain` | string | Substring match on `qname`; `%`, `_` and `\` are escaped before the `LIKE`. |
| `status` | string | Exact `verdict`: `allowed`, `blocked`, `whitelisted`, `rewritten`, `stale`. |
| `qtype` | u16 | Exact numeric record type. |
| `from` | i64 | Inclusive lower bound on `ts`, unix milliseconds. |
| `to` | i64 | Inclusive upper bound on `ts`, unix milliseconds. |
| `limit` | usize | Default `50`; clamped to `1..=500`. `0` becomes `1`; values above 500 become 500. |
| `cursor` | string | Opaque value from the previous response's `next_cursor`. Omit for the first page. |

Response: `200 application/json` with `QueryLogPage`:

```json
{
  "items": [
    {
      "id": 1042,
      "ts": 1763899200123,
      "client_ip": "192.0.2.10",
      "client_name": "laptop",
      "qname": "example.com",
      "qtype": 1,
      "rcode": 0,
      "verdict": "allowed",
      "upstream": "1.1.1.1",
      "elapsed_us": 1234,
      "dnssec": "secure",
      "proto": "udp"
    }
  ],
  "next_cursor": "AQAAAZqwldJ7AAAAAAAABBIxMjM0NTY3OA"
}
```

`id` is present for stored rows. Optional entry fields are omitted when absent
rather than emitted as `null`: `rule`, `list_source`, `client_name`, `rcode`,
`upstream`, `elapsed_us` and `dnssec` may be missing. `next_cursor` is always
present as a field and is `null` on the last page. The response has no total
count.

Other responses:

| Status | Body | When |
|---|---|---|
| `400` | `ProblemDetails` | `cursor` is not valid base64url, has the wrong payload length, has an unsupported version, or was issued for a different filter set. |
| `401` | `ProblemDetails` | No valid session cookie or bearer token. |
| `403` | `ProblemDetails` | Authenticated but not authorized for this endpoint (it requires Viewer). |
| `429` | `ProblemDetails` + `Retry-After` | Per-IP query-log budget (120 requests/minute, `Retry-After: 1`) or the account-wide API budget is exhausted (`Retry-After` up to 60). |
| `500` | `ProblemDetails` | The stats database read failed. |

### 27.3 Cursor lifecycle

1. **First page.** Send the filters and no `cursor`. The newest page is
   returned; keep `next_cursor`.
2. **Next page.** Send the same filter values plus `cursor=<previous
   next_cursor>`, unchanged. `limit` may change: it is not part of the cursor's
   filter binding.
3. **Last page.** `next_cursor` is `null`. Stop. Do not send `null` as a cursor
   string; omit the parameter.
4. **Filter change.** Any change to `client`, `domain`, `status`, `qtype`,
   `from` or `to` invalidates the cursor. An empty value (`?client=`) is a
   present filter and hashes differently from omitting the parameter, so keep
   the filter query string identical while paging. Restart without a cursor.
   Replaying the old cursor is `400` with detail `cursor does not belong to the
   current filter set; restart from the first page`.
5. **Malformed cursor.** Bad base64url, a wrong payload length or an unsupported
   version is also `400`. Never construct or edit a cursor; its payload is a
   versioned `(ts, id)` keyset position plus a filter hash and is not a public
   format.
6. **No snapshot.** Pages are ordered by `(ts, id)` descending with `id` as the
   tie-breaker. The next page starts strictly below the last returned row. Rows
   inserted at a newer position are not seen by later pages; deleted rows
   disappear; remaining rows do not duplicate or skip.
7. **No total.** There is no count in the response and the page read does not
   run `COUNT(*)`. Use `next_cursor: null` to detect the end.
8. **UI history mode.** A cursor-less request is the live first page; a request
   with a cursor is an explicit history page and pauses live polling. A filter
   change or refresh clears the cursor and returns to live mode.

### 27.4 Upstream config alias

| Path | Method | Result |
|---|---|---|
| `/api/v2/upstream` | `GET`, `PUT` | Canonical upstream configuration. Requires **Operator**. |
| `/api/v2/upstream/config` | `GET`, `PUT` | `308 Permanent Redirect`, `Location: /api/v2/upstream`, empty body. Requires **Operator** first: unauthenticated is `401`, insufficient role is `403`, only then the redirect. |

`308` preserves the method and body, so a `PUT` client that follows redirects
still sends its payload to `/api/v2/upstream`. A client that does not follow
`308` must update the path itself.

### 27.5 Status, errors and caching

`/health` is the generic probe: `200 {"status":"ok"}` when ready and
`503 {"status":"unavailable"}` when not (BC-4). It has no component detail.

`GET /api/v2/status` (Viewer) returns:

| Field | Type | Notes |
|---|---|---|
| `version` | string | Running server version. |
| `uptime_seconds` | u64 | Process uptime. |
| `role` | string | `master` or `slave`. |
| `listeners` | string[] | Bound listener descriptions. |
| `ready` | bool | Same aggregate verdict as `/health`. |
| `reasons` | object[] | `component`, `code`, `message` and optional `since_unix_ms`, in component order. |
| `acme` | object? | Omitted when ACME is disabled; otherwise `enabled`, `ready`, `http01_available`, `tls_alpn_available` and optional `reason`/`last_error`. |

`GET /api/v2/config` (Admin) returns `{"config_toml":"config_version = 2\\n..."}` with
secret values masked; a `500` means the on-disk file could not be read.
`GET /api/v2/config/restart-required` (Admin) returns
`{"restart_required_fields":[...],"message":"...","apply_endpoint":"/api/v2/config"}`.

Handler errors use RFC 7807 `application/problem+json`. Framework-generated
client errors (malformed JSON/query/path, `413 Payload Too Large`,
`415 Unsupported Media Type`, `405 Method Not Allowed`, a non-upgradable
WebSocket request) use the same envelope and media type; a 405 keeps its
`Allow` header. The unknown-path fallback
(`404`, including every `/api/v1...` path) carries the same `ProblemDetails`
body as `application/json`. The complete inventory, header rules and the A3
keep/unify decisions are in [API errors](2.0-api-errors.md).

```json
{
  "type": "https://sito.network/errors/409",
  "title": "Conflict",
  "status": 409,
  "detail": "the server's explanation",
  "restart_required": ["web.bind"]
}
```

`type`, `title`, `status` and `detail` are always present. `instance` is
optional and omitted when unset; `restart_required` is present only on a
restart-only `409`, as an array of dotted field names. A restart-only `409`
persists nothing.

| Status | Client-visible rule |
|---|---|
| `201` | Create endpoints return the created DTO (`/clients`, `/clients/groups`, `/filtering/lists`, `/rewrites`, `/auth/users`, `/auth/tokens`). Accept `201`; do not require `200`. |
| `400` | Invalid input, cursor, rewrite, reference or token scope. Nothing was persisted. |
| `401` | Missing/invalid session or bearer token, invalid login credentials, missing/invalid/expired/used `X-Reauth-Token`. |
| `403` | Insufficient role, CSRF failure, cross-origin WebSocket upgrade, or an API token attempting session re-authentication. |
| `404` | Unknown path, including every `/api/v1...` path; the fallback body is `ProblemDetails` JSON with `Content-Type: application/json`. |
| `405` | Method not registered for a matched path. `ProblemDetails` with `Content-Type: application/problem+json` and the original `Allow` header. |
| `409` | Restart-only config write/restore (with `restart_required`), referenced group/list conflict, generation conflict, concurrent/in-systemd update, an unknown version requiring `force`, or a mutating request on an HA replica slave (`type: urn:sito:ha:read-only`, optional `X-Dnsd-Master`). |
| `413` | Request body exceeds a limit. `ProblemDetails` with `application/problem+json`. |
| `415` | Missing or unsupported `Content-Type` on a JSON endpoint. `ProblemDetails` with `application/problem+json`. |
| `422` | JSON body is valid but does not match the endpoint schema. `ProblemDetails` with `application/problem+json`. |
| `426` | `/querylog/stream` handshake is syntactically valid but the connection cannot be upgraded (no upgrade state, e.g. a direct HTTP/1.1 request). Invalid `Connection`/`Upgrade`/version/key headers are `400`. `ProblemDetails` with `application/problem+json`. |
| `429` | Login/lockout, query-log per-IP budget or account-wide API budget. When `Retry-After` is present, back off for that interval. |
| `500` | Config file or stats database read failure, or an internal handler failure (for example an integration-list apply error). |
| `501` | HA endpoint on a build without the `ha` feature; the `ProblemDetails.detail` names `ha_not_supported` and `type` is `urn:sito:ha:not-supported`. Route authorization still runs first. |
| `502` | Integration-list fetch failed (upstream downloader/SSRF/parse failure). `ProblemDetails` with `application/problem+json`. |
| `503` | First-boot gate on a non-auth `/api/v2` path. The body is the deliberately plain-text `Setup not completed` signal consumed by `sito healthcheck`, not a `ProblemDetails` body. HA handlers may also return a `ProblemDetails` 503 when replication is not active. |

Authenticated `/api/v2` responses, `/metrics` and `/ui/` carry
`Cache-Control: no-store` and `Vary: Cookie`. Shared caches must not reuse them.

Client-visible redaction: the filtering **UI** reduces configured filter-list
URLs, runtime/integration `source_url` values and URLs embedded in refresh
errors to scheme+host for roles below Operator. The API JSON itself is not
redacted. Operators see the full source in the UI; a Viewer UI client must not
depend on the full URL.

Rate limits: the account-wide ceiling is
`auth.api_rate_limit_per_minute` (default `600`; `0` disables it) and is charged
once per authenticated request; a rejection is `429` with `Retry-After` up to 60
seconds. `GET /api/v2/querylog` additionally has a per-IP budget of 120
requests/minute with `Retry-After: 1`. Login and re-authentication lockouts also
return `429`.

### 27.6 Examples

Login, obtain a one-use re-authentication ticket, then mint an Admin-scoped API
token. Use a cookie jar so the session and CSRF cookies are carried; over TLS
the session cookie is `__Host-sito_session` and curl handles it automatically.

```bash
BASE=http://127.0.0.1:8080   # use https:// to receive the __Host- session cookie
JAR=$(mktemp)
curl -sS -c "$JAR" -H 'Content-Type: application/json' \
  -d '{"user":"admin","pass":"change-me"}' \
  "$BASE/api/v2/auth/login" | jq .
CSRF=$(awk '$6 == "sito_csrf" {print $7}' "$JAR")
REAUTH=$(curl -sS -b "$JAR" -H "Origin: $BASE" -H "X-CSRF-Token: $CSRF" \
  -H 'Content-Type: application/json' \
  -d '{"password":"change-me"}' \
  "$BASE/api/v2/auth/reauth" | jq -r .reauth_token)
# Add "code":"123456" to the body above when TOTP is enabled.
TOKEN=$(curl -sS -b "$JAR" -H "Origin: $BASE" -H "X-CSRF-Token: $CSRF" \
  -H "X-Reauth-Token: $REAUTH" -H 'Content-Type: application/json' \
  -d '{"name":"api-admin","scope":"admin"}' \
  "$BASE/api/v2/auth/tokens" | jq -r .token)
```

The re-authentication ticket is single-use and is consumed by the token
creation; request a fresh ticket for another sensitive Admin mutation. The
Admin token can perform every call below (Admin > Operator > Viewer).

First page, next page, end page, and the filter-mismatch `400`:

```bash
PAGE1=$(curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/querylog?limit=2")
CURSOR=$(echo "$PAGE1" | jq -r '.next_cursor // empty')
# The 400 example needs at least three matching rows: with limit=2 a cursor is
# emitted only when a third row exists. Stop if CURSOR is empty.

PAGE2=$(curl -sS -H "Authorization: Bearer $TOKEN" --get \
  --data-urlencode "cursor=$CURSOR" \
  --data-urlencode "limit=2" \
  "$BASE/api/v2/querylog")
echo "$PAGE2" | jq '{count: (.items | length), next_cursor}'
# Repeat with each new cursor; next_cursor: null means end of history.

curl -sS -i -H "Authorization: Bearer $TOKEN" --get \
  --data-urlencode "cursor=$CURSOR" \
  --data-urlencode "status=blocked" \
  "$BASE/api/v2/querylog"
# HTTP/1.1 400 Bad Request
# {"type":"https://sito.network/errors/400","title":"Bad Request",
#  "status":400,
#  "detail":"cursor does not belong to the current filter set; restart from the first page"}
```

Status, restart-only preview, upstream `308`, and the removed v1 surface:

```bash
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/api/v2/status" \
  | jq '{version,ready,reasons}'
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/api/v2/config" \
  | jq -r .config_toml | head
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/config/restart-required" | jq .
curl -sS -i -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/upstream/config"
# HTTP/1.1 308 Permanent Redirect
# location: /api/v2/upstream
curl -sS -i -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/status"
# HTTP/1.1 404 Not Found
# Content-Type: application/json   (unknown-path fallback ProblemDetails)
```

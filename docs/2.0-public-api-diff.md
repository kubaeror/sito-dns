# 2.0 Public API Diff

This document records the public API, crate and feature changes introduced by
the Phase 1 foundation work packages. Sections 1-4 describe **WP-1.1 —
Freeze/cut non-core features and dead code**; section 5 describes **WP-1.2 —
Normalized domain and client identity model**; sections 6-8 describe **WP-1.3
— Config v2 schema and one validator**; section 9 describes **WP-1.4 — staged
runtime generation and atomic apply**; section 10 describes **WP-1.5 — module
splits**; section 11 describes **WP-1.6 — shared response shaping and cache
keys**; section 12 describes **WP-1.7 — error, health and readiness policy**;
section 13 describes **WP-1.8 — test harness, mocks, and deterministic
timing**; section 14 describes **WP-1.9 — fuzz, benchmarks and CI gates**.
It is the migration reference for code
that depended on the 1.9.x workspace. The operator-facing
[`docs/2.0-migration.md`](2.0-migration.md) links here and maps the stable
breaking-change IDs to migration steps.

The changes are source-breaking for consumers of the internal workspace
crates. The WP-1.1/1.2 sections below do not change the `sito` binary's TOML
schema or API; WP-1.3 (sections 6-8) deliberately changes the TOML schema,
admin write semantics and CLI for 2.0.

## Breaking-change index

These IDs are stable. Every operator-visible or source-breaking change in this
document has one, and [`docs/2.0-migration.md`](2.0-migration.md) maps each ID
to a migration step and the affected document/test. The
[`scripts/check_migration_guide.py`](../scripts/check_migration_guide.py)
checker fails when a BC ID listed here has no concrete migration step.

| ID | Change | Sections |
|---|---|---|
| BC-1 | Config v2 is required; unknown keys/tables are rejected and a v1 document must be migrated | §6-§8 |
| BC-2 | New-install safe defaults change (`web.bind` loopback, `metrics_auth`, fail-closed filtering, ACME bootstrap opt-in); upgrades stay behavior-preserving unless `--adopt-safe-defaults` | §6 |
| BC-3 | Admin config writes that touch restart-only fields return 409 and persist nothing | §7-§8 |
| BC-4 | `/health` becomes a generic 200/503 probe; component details move to `/api/v1/status` and `/api/v1/ha/status` | §12 |
| BC-5 | RouterOS moves to the optional `sito-routeros` crate and several public items move or become private | §1-§2 |
| BC-6 | Internal workspace Rust APIs changed (domain/identity, runtime generation, response shaping, health/readiness, test fixtures) | §2, §5-§14 |

## 1. RouterOS is now an optional crate

RouterOS DHCP lease synchronization (HTTP client, response parsing and the
background sync task) moved out of `sito-clients` into the new optional
`sito-routeros` crate. **The default `sito` build does not link it.**

| Before (1.9.5) | After (2.0) | Notes |
|---|---|---|
| `sito_clients::routeros::RouterOsConfig` | `sito_clients::RouterOsConfig` (unchanged path) | Plain serde data type only; no `reqwest`. |
| `sito_clients::RouterOsError` | `sito_routeros::RouterOsError` | Moved; adds `MissingTokenEnv` for a configured but unresolvable `token_env` (no basic-auth fallback). |
| `sito_clients::fetch_routeros_leases` | `sito_routeros::fetch_routeros_leases` | Moved. |
| `sito_clients::spawn_routeros_sync` | `sito_routeros::spawn_routeros_sync` | Moved. |
| `sito_clients::routeros::{RawRouterOsLease, ROUTEROS_REQUEST_TIMEOUT, build_routeros_client}` | `sito_routeros::{RawRouterOsLease, ROUTEROS_REQUEST_TIMEOUT, build_routeros_client}` | Moved. `RawRouterOsLease::into_lease` now takes `verified: bool`. |
| `sito_clients::RouterOsLease` | `sito_clients::RouterOsLease` (same path) | Registry matching stays in `sito-clients`; the struct gains `verified: bool`, true only for `https://` with certificate verification. Unverified leases are display-only and never identify clients. |
| `sito_clients` dependency `reqwest` | removed | The default build no longer links the RouterOS HTTP stack. |

### Build and feature changes

```toml
# crates/sito/Cargo.toml
[features]
routeros = ["dep:sito-routeros", "sito-api/routeros"]
```

| Crate | Feature | Effect |
|---|---|---|
| `sito` | `routeros` | Adds `dep:sito-routeros` and forwards `sito-api/routeros`. Not in `default`. |
| `sito-api` | `routeros` | Internal capability flag: configuration validation accepts an enabled `[integrations.mikrotik]`. It does not add a dependency. |

The optional crate honours the D15 security bar: environment proxies are
disabled (`.no_proxy()`), error bodies are capped at 4 KiB, a configured but
unresolvable `token_env` is an error rather than a basic-auth fallback, and a
lease is identity-capable (`verified = true`) only when **both** conditions
hold: the `url` uses `https://` and `allow_invalid_certs = false`. A plaintext
`http://` URL (even with `allow_invalid_certs = false`) and an insecure-TLS
client both produce `verified = false`; such leases are display-only and the
registry never grants a group/trusted/MAC identity from them. The sync task
logs an explicit warning for either case, and `enabled = true` with a scheme
other than `http://`/`https://` is rejected by config validation.

```bash
cargo build -p sito                       # default: no sito-routeros
cargo build -p sito --features routeros   # optional integration included
```

`cargo tree -p sito --locked` must not contain `sito-routeros`;
`cargo tree -p sito --features routeros --locked` must contain it. The
integration remains **experimental**.

The default binary still links `reqwest` for unrelated features (ACME
HTTP-01/TLS-ALPN and the self-updater); the RouterOS-specific proof is the
absence of the `sito-routeros` crate and the rejection of an enabled
`[integrations.mikrotik]`.

A build without the feature rejects `[integrations.mikrotik] enabled = true`
during startup, `check-config` and API writes with an error naming the
`routeros` feature. It is never silently ignored. A disabled section is still
accepted in every build.

## 4. Non-Unix fallbacks

`sito-transport` already refuses non-Unix targets with `compile_error!` in
`lib.rs`, `udp.rs` and `pktinfo.rs`. The unreachable `#[cfg(not(unix))]`
permission fallbacks in `acme.rs` and the redundant `#[cfg(unix)]` gates were
deleted; Unix-only code is now unconditional inside the crate. Windows remains
unsupported.

## 5. WP-1.2 — Normalized domain and client identity model

WP-1.2 introduces canonical domain/network primitives in `sito-core` and moves
client policy onto an explicit identity-with-provenance model. It addresses
P1-9, P2-31..P2-35, P2-97..P2-99 and the IDN gaps.

### 5.1 New `sito-core::domain` API

```rust
pub struct NormalizedDomain(/* lowercase ASCII/punycode */);

impl NormalizedDomain {
    pub fn parse(raw: &str) -> Result<Self, DomainError>;      // IDN + wildcard + root
    pub fn parse_ascii(raw: &str) -> Result<Self, DomainError>; // historical wire form
    pub fn parse_idna(raw: &str) -> Result<Self, DomainError>;  // wire form with IDN
    pub fn root() -> Self;
    pub fn as_str(&self) -> &str;
    pub fn is_root(&self) -> bool;
    pub fn has_wildcard_labels(&self) -> bool;
    pub fn matches_suffix(&self, suffix: &Self) -> bool;
    pub fn is_strict_subdomain_of(&self, suffix: &Self) -> bool;
    pub fn into_string(self) -> String;
}
```

`NormalizedDomain` implements `Display`, `FromStr`, `TryFrom<&str>`,
`TryFrom<String>`, `Serialize` and `Deserialize`. Deserialization normalizes
(therefore `"EXAMPLE.COM."` becomes `"example.com"`), and serialization always
emits the canonical form.

`parse` converts raw Unicode/IDN labels to punycode, lowercases ASCII, strips
one trailing dot, validates label (63-byte) and name (253-byte) limits, keeps
wildcard labels (`*`, `*.example.com`, `*.banner.*`), and represents the root
as `"."`. `parse_ascii` and `parse_idna` preserve the historical wire contract:
raw Unicode, wildcards and the root are rejected where they were rejected
before. `DomainError` mirrors the former `ProtoError` normalization variants.

`sito_proto::normalize_domain` and `normalize_domain_or_idna` now delegate to
these constructors and map `DomainError` back to `ProtoError`, so their public
signatures and error type are unchanged.

### 5.2 New `sito-core::net` API

```rust
pub struct IpNetwork { /* address + prefix */ }

impl IpNetwork {
    pub fn new(addr: IpAddr, prefix: u8) -> Result<Self, CidrError>;
    pub fn parse(value: &str) -> Result<Self, CidrError>;
    pub fn addr(&self) -> IpAddr;
    pub fn prefix(&self) -> u8;
    pub fn contains(&self, target: IpAddr) -> bool;
    pub fn network_address(&self) -> IpAddr;
}

pub fn ip_in_subnet(network: IpAddr, prefix: u8, target: IpAddr) -> bool;
```

`IpNetwork` implements `Display`, `FromStr` and `Hash`. `CidrError` rejects
missing/extra separators, unparsable addresses and prefixes larger than 32
(IPv4) or 128 (IPv6). Membership tests always mask host bits and never match
across address families.

### 5.3 New `sito-core::client` API and `ClientContext` migration

```rust
pub enum IdentitySource {
    Ip, Cidr, Mac, TlsSni, DohPath, Secret, RouterOs,
}

pub struct ClientIdentity {
    pub ip: IpAddr,
    pub source: IdentitySource,
    pub authenticated: bool,
    pub name: Option<String>,
    pub group: Option<String>,
    pub mac: Option<String>,
}

impl ClientIdentity {
    pub fn from_context(ctx: &ClientContext) -> Option<Self>;
    pub fn may_match_secret_rules(&self) -> bool;
    pub fn may_match_client_exception(&self) -> bool;
}
```

`IdentitySource::is_trusted` follows D10: `Ip`, `Cidr`, `Mac`, `Secret` and
verified `RouterOs` are identity-capable; `TlsSni` and `DohPath` are
display/statistics-only. The two `may_match_*` methods are true only when the
identity is both authenticated and from a trusted source. The serde name of
every variant matches `IdentitySource::as_str()` (including `routeros`).

`ClientIdentityRef<'a>` is the borrowed form used on hot paths; it exposes
`ip`, `source`, `authenticated`, `name: Option<&str>`, `group` and `mac`, plus
the same `may_match_*` methods. `ClientContext::identity_ref()` returns it
without cloning strings.

`ClientContext` gains:

| Field / method | Change | Notes |
|---|---|---|
| `identity_source: Option<IdentitySource>` | new, `#[serde(default, skip_serializing_if = "Option::is_none")]` | Older serialized contexts deserialize with `None`. |
| `identity_ref()` / `identity()` | new | Borrowed and owned policy identities. Legacy in-process contexts that only populated `client_name`/`group` are treated as an authenticated IP identity; registry-produced contexts always carry an explicit source. |
| `may_match_secret_rules()` / `may_match_client_exception()` | new | Convenience wrappers over `identity_ref()`. |
| `ClientContext::with_id` | behaviour | Records `IdentitySource::DohPath`, unauthenticated. |
| `ClientContext::with_sni` | behaviour | Records `IdentitySource::TlsSni`, unauthenticated. |
| `ClientContext::with_authenticated_id` | behaviour | Records `IdentitySource::Secret` in addition to `id_authenticated = true`. |

`ClientRegistry::resolve` now records the matching source: exact IP (`Ip`),
CIDR (`Cidr`), ARP MAC configured on an entry (`Mac`), verified RouterOS lease
(`RouterOs`), configured secret (`Secret`), and otherwise the untrusted
wire-claimed `TlsSni`/`DohPath` label. A trusted RouterOS lease hostname copied
into `client_name` keeps `RouterOs` provenance. An unverified RouterOS lease
still never grants identity (WP-1.1 rule preserved). This tree has no
`trust_arp` setting; a MAC is identity only when the operator lists it on a
client entry, which is the configured-MAC-identity case of D10.

### 5.4 Policy now uses identity, never `ctx.id`

| Crate | Change | Migration |
|---|---|---|
| `sito-filter` | `$client` name/group/MAC matching requires `ClientIdentity::may_match_client_exception()`. | Wire-claimed DoH path/SNI labels never satisfy `$client`; IP/CIDR matchers still use the query source address. |
| `sito-rewrites` | `exception_clients` matches only an authenticated identity's name/group/MAC, or an IP/CIDR. | A raw `ClientContext::id` (even a registry-authenticated secret) no longer satisfies an exception; match the resolved client name/group/MAC instead. |

The `ctx.id` audit found no remaining policy use. `sito-clients` still consumes
`ctx.id` during identification (it is the credential being matched) and
transport/stats/tests use it for display only.

### 5.5 Other source-breaking changes

| Crate | Item | Change | Migration |
|---|---|---|---|
| `sito-filter` | `parser::ClientMatcher::Cidr { ip, prefix }` | replaced with `Cidr(IpNetwork)` | Use `IpNetwork::parse`/`IpNetwork::new`. |
| `sito-filter` | `parser::cidr_matches` | removed | Use `sito_core::ip_in_subnet` or `IpNetwork::contains`. |
| `sito-filter` | `parser::RuleModifiers::denyallow` | `Option<Vec<String>>` → `Option<Vec<NormalizedDomain>>` | Compare with `as_str()`/`matches_domain_suffix`; values are canonical punycode. |
| `sito-filter` | list pattern parsing | raw Unicode (IDN) domains, whole-label wildcards and prefix patterns are now accepted and normalized to punycode instead of silently dropping or never matching the rule; exact keys reject wildcard labels | Existing ASCII lists are unchanged. |
| `sito-cache` | `DnsCache::invalidate_domain` | normalizes the requested name with IDNA before matching cache keys, so Unicode names evict punycode entries | Callers may keep passing `Name::to_string()`; no API change. |
| `sito-rewrites` | rewrite domain parsing | invalid entries are skipped with a warning instead of being compared in raw form | Fix the config entry; valid IDN/trailing-dot entries still normalize. |

# WP-1.3 — Config v2 schema and one validator

Section 6 describes the config v2 freeze. The user-facing contract changes are
breaking for 2.0 (Phase 1 may break config/API contracts per the release
mapping); source consumers of the internal crates should follow the table.

## 6. Config schema and defaults

| Before (1.9.x / WP-1.2) | After (2.0) | Migration |
|---|---|---|
| `config_version` default `1`; only `1` accepted | default `2`; only `2` accepted | Run `sito config migrate --from v1 --to v2 --backup`. A v1 document is rejected with that command in the error. |
| Unknown TOML keys/tables silently ignored | Rejected at parse time (typed `deny_unknown_fields` + map walk for legacy raw sections) | Remove the key, or use `--ignore-unknown-keys` **only** during migration. |
| `[web] bind` default `"0.0.0.0"` | `"127.0.0.1"` | Migrated v1 files keep `0.0.0.0`; pass `--adopt-safe-defaults` to opt into loopback. New installs get loopback. |
| `[dns.tls]` preferred over `[tls]` | Typed `[tls]` is canonical; `[dns.tls]` remains a deprecated alias for one alpha | `sito config migrate` moves it to `[tls]`. |
| `[web] acme_*` legacy keys | Typed `[acme]` canonical; `[web] acme_*` deprecated for one alpha | `sito config migrate` moves them to `[acme]`. |
| `stats.query_log_retention_days`, `privacy.anonymize_client_ip` aliases | Still accepted; canonical keys are `stats.retention_days` and `privacy.anonymize_querylog` | `sito config migrate` rewrites them. |
| `auth.admin_password_hash`, `auth.tokens`, `integrations.mikrotik.token` tolerated | Removed: rejected by the v2 parser | Migration drops and reports them. Sessions/tokens live in `data_dir` stores. |
| Duplicate `dns.bind`, web/DNS port collisions, empty `server.data_dir`, bad upstream targets, invalid ACME domains, bad `[integrations.lists]` accepted until later runtime failure | Rejected by `Config::validate_full()` | Fix the value; the error names the dotted field. |

The schema is frozen here. Any later field must be optional with a default or
land in a v2.1 migration. `clients.trust_arp` is deliberately **not** part of
v2; it is deferred to WP-2.5 (optional, default `false`).

not produced by the schema fixture.

### `sito` CLI

| Command | Change |
|---|---|
| `sito config migrate --from v1 --to v2 --backup` | new. Flags: `--adopt-safe-defaults`, `--ignore-unknown-keys`, `--json`, `--config <path>`. |

Exit codes: `0` on success; non-zero on a rejected migration. The original

## 8. REST API changes (existing `/api/v1`)

| Endpoint | Change |
|---|---|
| `PUT /api/v1/config` | Returns **409 Conflict** with `restart_required` and does **not** persist when a restart-only field changes. Previously it applied hot fields, persisted everything, and reported `restart_required`. |
| `POST /api/v1/config/restore/confirm` | Same 409/no-persist rule for restored configurations. |
| `GET /api/v1/config/restart-required` | New read-only preview of the restart-only matrix (`RestartRequiredResponse`). `/api/v2` remains Phase 2 work. |
| `POST /api/v1/config/reload` | Unchanged response shape; it still reports restart-only fields because the file is already on disk (an operator edit). |

`docs/openapi.json` carries the new path and the optional
`ProblemDetails.restart_required` field.

WP-1.4 also returns **409 Conflict** when a configuration write's expected
runtime generation changed while it was staged (`GenerationConflict`), and
`POST /api/v1/filtering/refresh` returns 409 when a config apply landed before
its refresh could publish. Retry the request; nothing was published.

# WP-1.4 — Staged runtime generation and atomic apply

There are no TOML schema or REST contract changes in WP-1.4. The changes are
source-level for embedders that published runtime components directly; the
admin API, HA push, restore and file watcher now share one staged apply and
publish exactly one runtime generation.

## 11. WP-1.6 — shared response shaping and cache keys

Every DNS response path (cache hit, stale fallback, upstream, local rewrite,
safe-search and synthesized blocked/error answers) now runs through one
`sito_proto::ResponseShaper`. The envelope is derived exclusively from the
current client query; the cached/upstream/local message is treated as data.
`docs/audit6-test-matrix.md` maps the WP-1.6 tests.

### `sito-core`

| Item | Change | Migration |
|---|---|---|
| `DnssecMode` | moved to `sito_core::dnssec::DnssecMode` and re-exported as `sito_core::DnssecMode` | `sito_dnssec::DnssecMode` is still valid (re-export). The move lets `sito-proto` shape responses without depending on the validator crate. |

### `sito-proto`

| Item | Change | Migration |
|---|---|---|
| `ResponseShaper` | new unit struct; `ResponseShaper::shape(response, client_query, dnssec_mode)` is the §10.4/§10.7 contract | Call it last on every response path. It copies ID/opcode/question/RD/CD from `client_query`, sets QR/RA and clears AA, rebuilds OPT for EDNS clients only, clears AD when the client did not signal DNSSEC awareness (or CD=1, or validation is disabled), and strips DNSSEC records for DO=0 clients. |
| `ResponseShaper::shape_with_payload(response, client_query, dnssec_mode, payload_size)` | new; the pipeline passes `dns.edns_udp_size` so the OPT CLASS advertises the resolver's receive size | Use `shape` when no listener configuration is available (defaults to `DEFAULT_EDNS_PAYLOAD` = 1232). |
| `DEFAULT_EDNS_PAYLOAD` | new constant (`1232`) | Default resolver UDP payload for embedders/tests. |
| `strip_dnssec_records(response)` | new public helper (moved from the private pipeline helper) | Removes RRSIG/NSEC/NSEC3/DNSKEY and DAU/DHU/N3U. The shaper calls it for DO=0 clients. |

### `sito-cache`

| Item | Change | Migration |
|---|---|---|
| `CacheKey::for_query(query)` | new canonical constructor (§10.7 interface) | Use it instead of `from_query`; `from_query` remains as an alias with identical behavior. |
| `CacheKey::edns` | new field: whether the query carried an OPT record | A non-EDNS client (512-byte UDP ceiling) and an EDNS client no longer share an entry. Unknown/COOKIE/NSID/padding options are **not** keyed and are sanitized by the shaper. |
| `CachePolicyEpoch` | new type alias of `PolicyEpoch` (and therefore `sito_runtime::RuntimeGeneration`) | There is still exactly one generation counter (P-5); use the alias where the cache-policy interface name is clearer. |
| `DnsCache::update_config` | now re-clamps every still-fresh entry to the new `min_ttl`/`max_ttl`/`negative_ttl_max` policy and drops entries past the new stale window | A lowered `max_ttl` immediately caps served TTLs; a raised `min_ttl` raises unvalidated entries (Secure keeps floor 0). Entries whose original lifespan passed are not resurrected as fresh. |
| `DnsCache::insert` | now always stores `ValidationStatus::Unchecked`; it no longer derives `Secure` from an upstream AD bit | Callers that validated must use `insert_with_status`/`insert_with_status_at_epoch`. |
| `DnsCache::get`/`get_stale`/`insert` name-only helpers | retained, but they operate on the default (`edns = false`, DO=0, CD=0, no ECS) keyspace | Production and tests use the `*_for_query*` helpers so DO/CD/ECS/EDNS cannot cross-serve. |

### Behavior notes

- A non-EDNS client never receives an OPT record; an EDNS client receives a
  fresh OPT with the resolver payload size, the client's DO bit and (if
  present) the RFC 8914 EDE diagnostic only.
- CD=1 responses never assert AD and never share a cache entry with CD=0 (the
  key already separated them; the shaper now keeps the flag coherent).
- `TC` is preserved by the shaper; response size/truncation remains owned by
  the transport/framing layer (WP-1.6 does not change P1-14 behavior).
- A reload advances the runtime/cache generation as in WP-1.4; the TTL
  re-clamp additionally makes the cache API correct when called directly or if
  a future generation policy keeps entries alive across a cache-only reload.

## 12. WP-1.7 — error, health and readiness policy

### `/health` is now a generic probe (breaking response shape)

| Before (1.9.x) | After (2.0) |
|---|---|
| Always `200` with `{status, setup_pending, ha:{required,ready,reason}, acme:{enabled,ready,reason}}` | `200 {"status":"ok"}` when ready; `503 {"status":"unavailable"}` when not |

The endpoint no longer exposes component names, reason codes, error strings,
filesystem paths, setup state or configuration values. Consumers that parsed
`setup_pending`/`ha`/`acme` from `/health` must use the admin API:
`GET /api/v1/status` (Viewer) carries `ready` and `reasons[]`, and
`GET /api/v1/ha/status` carries the detailed HA reason. The `sito healthcheck`
subcommand now treats a `503` (or a body without `status: ok`) as not ready and
uses the existing setup-pending middleware signal (`/api/v1/status` → `503
Setup not completed`) instead of a `setup_pending` field. It probes `/health`
whenever the admin listener answers, not only on HA nodes. `/health` does not
run the advisory stats database probe; `/status` does, bounded to 750 ms.


### `GET /api/v1/status`

Additive. The existing `version`, `uptime_seconds`, `role`, `listeners` and
`acme` fields are unchanged.

| Field | Type | Notes |
|---|---|---|
| `ready` | `bool` | Same aggregate verdict as `/health`. |
| `reasons` | `ReadinessReason[]` | Component/code/message/since, in component order. |
| `ReadinessReason.component` | `string` | `listeners`, `tls`, `acme`, `ha`, `filter`, `stats`. |
| `ReadinessReason.code` | `string` | Stable machine-readable code (for example `listener_bind_failed`). |
| `ReadinessReason.message` | `string` | Human summary; never contains secrets or certificate text. |
| `ReadinessReason.since_unix_ms` | `u64?` | Omitted when the failure start time is unknown. |

A stats database/writer outage is reported as `stats_unavailable` but does not
set `ready` to false. A retained filter snapshot (`FilterState::Failed` or
`Loading` with `unavailable == false`) is `filter_degraded`, also non-blocking;
only `unavailable == true` is not-ready. The D12 certificate ladder reports a
renewal failure or a certificate expiring within 30 days as degraded and an
expired certificate as not-ready. See `docs/runbook-ha.md` for the full
component matrix.

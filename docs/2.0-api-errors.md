# 2.0 `/api/v2` Error Envelope Audit (A3)

This document records the error-envelope audit for the 2.0 administrative API.
It is the reference for status codes, media types, bodies, stable reason fields
and headers that `/api/v2` can return. The migration contract stays in
[API diff §27.5](2.0-public-api-diff.md#275-status-errors-and-caching); this page
adds the complete inventory and the A3 decisions.

Scope: every error path reachable through `/api/v2` (handler errors, auth/RBAC
extractors, CSRF, setup and HA gates, framework extractor rejections, method and
media-type errors, the unknown-path fallback, and the OpenAPI description).
`/health`, `/metrics` and `/ui` are out of scope except where they share a
middleware with the API.

## 1. The envelope

Handler errors use RFC 7807 `ProblemDetails` with
`Content-Type: application/problem+json`:

```json
{
  "type": "https://sito.network/errors/409",
  "title": "Conflict",
  "status": 409,
  "detail": "the server's explanation",
  "instance": "/api/v2/clients",
  "restart_required": ["web.bind"]
}
```

| Field | Presence | Notes |
|---|---|---|
| `type` | always | `https://sito.network/errors/<status>` except `urn:sito:ha:read-only` (409 on an HA replica) and `urn:sito:ha:not-supported` (501 without the `ha` feature). |
| `title` | always | HTTP reason phrase, or the handler-specific title for update/HA errors. |
| `status` | always | Numeric status, equal to the HTTP status. |
| `detail` | always | Human-readable, occurrence-specific. Some handlers embed a stable token in the text (`ha_not_supported`); there is no separate `code` field. |
| `instance` | sometimes | The request path; present on the HA read-only gate. |
| `restart_required` | only on restart-only 409 | Dotted config field names; the write persists nothing. |
| `retry_after_secs` | never in the body | Rendered as the `Retry-After` header (see §3). |

The `type` URI is status-derived, not endpoint-specific. Clients must branch on
`status` (and, for the two HA `urn:` types, on `type`); do not treat `type` as a
fine-grained error code. Adding a `code` field would be a new API field and is
out of scope for A3.

## 2. Inventory

“Before A3” describes the tree at the A3 base commit. “After A3” is the
contract on this branch.

### 2.1 Handler and middleware errors

| Source / paths | Status | Content-Type (after A3) | Body | Headers | Decision |
|---|---|---|---|---|---|
| `RequireViewer` / `RequireOperator` / `RequireAdmin` on every protected operation | 401 | `application/problem+json` | `ProblemDetails` (`detail` names missing/invalid Bearer token, session cookie or credentials) | none | keep |
| same | 403 | `application/problem+json` | `ProblemDetails` insufficient role | none | keep |
| account-wide API budget (`auth.api_rate_limit_per_minute`) | 429 | `application/problem+json` | `ProblemDetails`; detail names the configured limit | `Retry-After` seconds (up to 60) | keep |
| `POST /auth/login` | 401 | `application/problem+json` | `ProblemDetails` invalid credentials / stale credentials | none | keep |
| `POST /auth/login`, `POST /auth/reauth`, `POST /auth/totp/verify` | 429 | `application/problem+json` | `ProblemDetails` lockout or per-IP/rate limit; detail carries remaining seconds when known | none (lockout is not an API-budget rejection) | keep; documented |
| `POST /auth/reauth` | 401/403 | `application/problem+json` | `ProblemDetails` invalid password/code or an API-token caller | none | keep |
| CSRF middleware (`Origin`/`Referer`, double-submit token) | 403 | `application/problem+json` | `ProblemDetails` | none | keep |
| CSRF form-body cap | 413 | `application/problem+json` | `ProblemDetails` | none | unify (was `text/plain`; see §4) |
| First-boot gate, `/api/v2/auth/*` | 403 | `application/problem+json` | `ProblemDetails` authentication disabled until setup completes | none | keep |
| First-boot gate, other `/api/v2/*` | 503 | `text/plain; charset=utf-8` | `Setup not completed` | none | **keep deliberately** (see §4) |
| HA replica slave, mutating method outside auth/resync | 409 | `application/problem+json` | `ProblemDetails`, `type` = `urn:sito:ha:read-only`, `instance` = path | `X-Dnsd-Master` when a master URL is configured | unify (was `application/json`; see §4) |
| `POST /querylog/clear`, `DELETE /querylog` | 429 | `application/problem+json` | `ProblemDetails` | `Retry-After: 1` (per-IP budget) | keep |
| `GET /stats`, `/stats/clients`, `/stats/upstreams` | 429 | `application/problem+json` | `ProblemDetails` | `Retry-After: 1` | keep |
| `GET /querylog` | 400/500 | `application/problem+json` | `ProblemDetails` (cursor mismatch, stats read failure) | none | keep |
| Config writes/restores, references, generation conflicts | 409 | `application/problem+json` | `ProblemDetails`; `restart_required` on restart-only writes | none | keep |
| Update endpoints | 400/409/500 | `application/problem+json` | `ProblemDetails` (Docker 400, systemd/in-progress/unknown-version 409, failure 500) | none | keep |
| HA status/slaves | 503 | `application/problem+json` | `ProblemDetails` replication not active | none | keep |
| HA resync | 429/503 | `application/problem+json` | `ProblemDetails` queue full / coordinator unavailable | none | keep |
| HA routes without the `ha` feature | 501 | `application/problem+json` | `ProblemDetails`, `type` = `urn:sito:ha:not-supported`, detail contains `ha_not_supported` | none | keep |
| Integration refresh | 400/404/502 | `application/problem+json` | `ProblemDetails` | none | keep |
| Unknown path under `/api/v2` (including every `/api/v1...` path) | 404 | `application/json` | `ProblemDetails` fallback body | none | **keep deliberately** (documented fallback; §4) |
| `GET\|PUT /upstream/config` after authentication | 308 | none | empty | `Location: /api/v2/upstream` | keep (redirect, not an error) |

### 2.2 Framework-generated client errors

These statuses are produced by Axum before a handler runs. Before A3 they used
`text/plain; charset=utf-8` or an empty body.

| Trigger | Status | After A3 | Headers |
|---|---|---|---|
| `Json` body is not valid JSON | 400 | `ProblemDetails`, `application/problem+json`; detail is Axum's parse message | none |
| `Query`/`Path` parameter fails to deserialize | 400 | same; detail names the parameter | none |
| Body exceeds the extractor limit | 413 | same | none |
| Missing or non-JSON `Content-Type` for a JSON endpoint | 415 | same | none |
| JSON is valid but does not match the schema | 422 | same | none |
| Method not registered for a matched path | 405 | same; detail is `The HTTP method is not allowed for this endpoint.` | `Allow` is preserved |
| `/querylog/stream` request cannot be upgraded (bad `Connection`/`Upgrade` header, HTTP/1.0) | 400 or 426 | same; detail is Axum's upgrade error | none |

## 3. Headers

| Header | When | Notes |
|---|---|---|
| `Retry-After` | 429 from the account-wide API budget | Seconds until the window resets (at most 60). |
| `Retry-After` | 429 from query-log or stats per-IP budgets | Always `1`. |
| `Retry-After` | 429 from login/TOTP/re-auth lockouts or HA resync queue | Not sent. The detail carries the wait time where known. This is unchanged and documented. |
| `X-Dnsd-Master` | HA replica read-only 409 | Present only when a master URL is configured; it is a hint, not an authorization header. |
| `Allow` | 405 | Preserved by the A3 normalizer. |
| `WWW-Authenticate` | any 401 | Not sent. `401` is a uniform JSON answer for Bearer, session and login/re-auth failures; no browser auth challenge is offered. Recorded as a deliberate residual, not an inconsistency between paths. |
| `Cache-Control: no-store`, `Vary: Cookie` | every `/api/v2` response | Added by the security-headers middleware, including errors. |

## 4. Decisions and evidence

| Decision | Evidence |
|---|---|
| **Unify framework 400/413/415/422/405 into `ProblemDetails`.** | The operations document `400` (and some `415`-class outcomes) with a `ProblemDetails` body, while Axum returned `text/plain` for malformed JSON/query/path and an empty body for 405. The same endpoint could therefore return two different bodies for the same status. The normalizer lives in `error::api_error_envelope_middleware`, scoped to `/api/v2`, client errors only, and only when the media type is missing or `text/plain`. |
| **Unify the HA read-only 409 media type.** | The gate built a correct `ProblemDetails` body but wrapped it in `Json`, yielding `application/json` while every other problem response is `application/problem+json`. One-line change to `problem.into_response()`; `X-Dnsd-Master` and the `urn:sito:ha:read-only` type are unchanged. |
| **Keep the unknown-path 404 as `application/json`.** | Explicitly documented in API diff §27.5 and §27.1, and the fallback also serves non-API paths. Changing it is not required by an inconsistency: the body is already `ProblemDetails`. |
| **Keep the first-boot `/api/v2` 503 as plain text.** | The gate runs before authentication; the text is documented in [first-time setup](first-time-setup.md) and the `sito healthcheck` setup fallback matches the body (`crates/sito/src/cli.rs`). Converting it would change a deliberate pre-auth signal with no envelope benefit, and the gate applies to API clients that have no session yet. |
| **Keep per-endpoint `ProblemDetails` details and titles.** | All handler errors already share the envelope, fields and media type. Handler-specific titles (`Update Check Failed`, `Read-Only Replica`, …) are documented and tested; they are not an inconsistency. |
| **Do not add a `code` field.** | `type` is the only stable machine field today. Adding `code` would be a new response field and is outside this audit. Two HA types already provide stable reasons. |
| **Do not change 429 header policy.** | The API-budget and polling budgets send `Retry-After`; lockout/queue rejections do not and have always relied on `detail`. Both are documented. |

### Compatibility note for UI/JS callers

- No success body, status, or `ProblemDetails` field changed.
- Handler errors were already `application/problem+json`; only the HA read-only
  409 media type changed from `application/json` to `application/problem+json`.
  Both are JSON with identical fields, and the bundled UI does not parse error
  bodies (HTMX renders the server response), so no UI behavior changes.
- Framework rejections changed from plain text/empty to a JSON problem body.
  Clients that only checked the status code are unaffected; clients that parsed
  the text body now get `detail` with the same message.
- The first-boot 503 body is unchanged; `sito healthcheck` keeps matching it.

## 5. OpenAPI

Before A3 `docs/openapi.json` advertised every error response as
`application/json` because `utoipa` derives that from `body = ProblemDetails`,
while the server sends `application/problem+json`. A modifier
(`ProblemJsonErrorContent`) now rewrites 4xx/5xx responses that reference
`#/components/schemas/ProblemDetails` to
`application/problem+json`. Success responses keep their declared media types
(JSON, or `application/gzip` for the backup download).

Framework statuses are not repeated on every operation. They are documented
here and share the same envelope; `test_api_framework_errors_use_problem_details`
locks the behavior down.

```bash

cargo test -p sito-api --all-features openapi
```

## 7. Residuals / out of scope

- `WWW-Authenticate` is still omitted on 401 (see §3).
- Login/TOTP/re-auth lockout 429s and the HA resync queue 429 do not send
  `Retry-After`.
- No per-endpoint machine `code` field; `detail` carries the only free-form
  reason.
- The setup gate still serves `text/plain` for non-auth `/api/v2` paths.
- `/health` (`application/json`) and `/metrics` (`text/plain` success;
  `ProblemDetails` errors) are outside `/api/v2` and unchanged.

# Migrating to sito 2.0

This is the upgrade guide for the **2.0.0-rc.2 candidate** (workspace version
`2.0.0-rc.2`). It covers the Phase 1 foundations, the post-Phase-1 HA
consolidation, the Phase 2 core-hardening work packages (WP-2.1 through
WP-2.13), and the Phase 3 verification evidence (WP-3.1 through WP-3.3). The
WP-3.4 release preparation and the deferred items listed in the
[current claim matrix](2.0-claim-matrix.md) are recorded there; the tag is
created only after the final gate and `main` CI.

## 1. Status and scope

| Line | Status | What it means for you |
|---|---|---|
| **1.9.5** | Published stable release | Keep this tag pinned until you deliberately move to the 2.0 line. |
| **2.0.0-rc.2** | Release candidate (tag pending) | Phase 3 verification at the rc.1 candidate; the tag is created after the final gate and `main` CI. No stable 2.0 artifact is published. |
| **2.0.0 stable** | Planned | Requires final 2.0 sign-off; installer/container `config.toml` auto-migration remains deferred. `/api/v2` is the only administrative API; `/api/v1` was removed. |

Phase 1 is implemented on this branch:

- config v2 with one validator and `sito config migrate` (WP-1.3);
- one staged runtime generation and atomic apply (WP-1.4);
- module splits with source-compatible re-exports (WP-1.5);
- one response shaper and cache TTL re-clamping (WP-1.6);
- generic `/health` plus detailed readiness (`/api/v2/status`) (WP-1.7);
- deterministic test harness/clock and shared fixtures (WP-1.8);
- fuzz, benchmark, coverage and dependency-hygiene gates (WP-1.9);
- normalized domain/client identity and optional RouterOS (WP-1.1/1.2).

Phase 2 core hardening is also implemented on this branch:

- DNSSEC chain state and negative-cache/policy integration (WP-2.1/2.2);
- filter parser/compiler budgets, precedence, groups and rewrites (WP-2.3/2.4);
- client policy, schedules, safe search and curated data (WP-2.5);
- transport admission, TLS manager set and QUIC lifetimes (WP-2.6);
- upstream bootstrap/SSRF/protocol correctness and per-attempt metrics (WP-2.7);
- cache shaping, invalidation and TTL policy (WP-2.8);
- HA protocol v2, failover and truthful publish outcomes (WP-2.9);
- auth/RBAC and self-service 2FA (WP-2.10);
- API/OpenAPI, config apply and updater hardening (WP-2.11);
- stats retention, PII and polling (WP-2.12);
- ops, Docker, systemd, installer and release hardening (WP-2.13);
- this documentation/migration truth pass and the legacy WebSocket
  query-token removal (WP-2.14).

The optional HA module and the portable `sito-ha-types` contract crate remain
part of the delivered tree. The API v2-only surface is delivered: `/api/v2` is
the only mounted administrative API and `/api/v1` was removed (§5.3).

**Deferred, not part of Phase 2 core hardening:** installer/Docker config
auto-migration; a default-deny
DNS client ACL; weighted upstream balancing;
edit-time read-only HA enforcement; optional external
parental/service data; and the remaining rc.1 tag/publication step. The
24-hour fuzz campaign is explicitly deferred by the operator. HA wire protocol v2
*is* implemented (see [§8.2](#82-ha-protocol-v2-upgrade)); it is a coordinated
cluster upgrade, not an in-place 1.9.x state migration.

## 2. Before you upgrade

1. Read the [breaking-change index](#3-breaking-change-index).
2. Stop the service so no process holds the config, database or service lease.
3. Back up the whole data directory **and** the configuration, including
   `config.toml`, `users.toml`, `totp.key`, `stats.db`, `stats-salt`, the ACME
   cache, HA certificates/key material, `ha_state.toml` and
   `ha_watermark.toml`:

   ```bash
   sudo systemctl stop sito
   sudo install -d -m 0700 /var/backups/sito-pre-2.0
   sudo tar -C /etc/sito -czf /var/backups/sito-pre-2.0/etc-sito.tgz .
   sudo tar -C /var/lib/sito -czf /var/backups/sito-pre-2.0/var-lib-sito.tgz .
   ```

4. Keep the previous **binary** (or container image tag) in the backup. A config
   rollback alone is not a complete rollback.

`--backup` on the migration command writes a private `config.toml.v1.bak`
(mode `0600`) next to the config; the full archive above additionally covers
the data directory.

## 4. Config v1 → v2

### 4.1 Run the migration

Only a `v1` → `v2` migration is supported. The command is explicit; installer
and container config auto-migration remain unimplemented and deferred (not part
of the delivered Phase 2 tree). The installer's `--no-migrate` and the
container's `SITO_NO_MIGRATE=1` apply only to the statistics database, not to
`config.toml`.

```bash
sudo systemctl stop sito
sudo sito config migrate --from v1 --to v2 --backup --config /etc/sito/config.toml
sudo systemctl start sito
```

`--from`/`--to` are required and only `v1` → `v2` is accepted. With
`--backup`, the original document is written atomically to
`<config>.v1.bak` (mode `0600`) before the replacement. The replacement is
written to a private sibling, fsynced and renamed, also `0600`.

The migration is **behavior-preserving** by default:

1. it parses the v1 document and rejects unknown keys unless
   `--ignore-unknown-keys` is given;
2. it copies every known v1 key/value, even when the 2.0 default differs;
3. it moves `[dns.tls]` into typed `[tls]`;
4. it moves `[web] acme_*` into typed `[acme]` (an existing canonical value
   wins and the conflict is reported);
5. it rewrites `stats.query_log_retention_days` → `stats.retention_days` and
   `privacy.anonymize_client_ip` → `privacy.anonymize_querylog`;
6. it drops removed/dead keys and reports them;
7. it writes `config_version = 2` and validates the result with the normal v2
   parser before the file is replaced.

The checked-in [`config-v1-to-v2-map.toml`](../crates/sito-core/config-v1-to-v2-map.toml)
enumerates every serde field and is embedded in the binary. A unit test
(`config::tests::test_config_map_covers_every_serde_field`) fails when the map
and schema diverge. The docs checker additionally verifies that every kept map
path and every deprecated alias target is documented in the configuration
reference.

### 4.2 Read the report

`--json` prints a machine-readable report:

```json
{
  "from_version": 1,
  "to_version": 2,
  "moved": [
    { "from": "web.acme_enabled", "to": "acme.enabled", "reason": "..." }
  ],
  "removed": [
    { "from": "auth.admin_password_hash", "reason": "..." }
  ],
  "unknown_dropped": [],
  "defaults_materialized": ["web.bind"],
  "safe_defaults_applied": [],
  "warnings": []
}
```

- `moved` lists aliases rewritten to their canonical path.
- `removed` lists keys rejected in v2 (`auth.admin_password_hash`,
  `auth.tokens`, `integrations.mikrotik.token`) and any v2-dead key.
- `unknown_dropped` is non-empty only with `--ignore-unknown-keys`.
- `defaults_materialized` lists values written to preserve v1 behavior (for
  example an omitted `web.bind`).
- `safe_defaults_applied` lists fields changed by `--adopt-safe-defaults`.
- `warnings` names alias conflicts and other review items.

### 4.3 Unknown keys and typos

Startup, `check-config`, API writes, backup restore and HA apply reject unknown
keys/tables by default. This prevents a typo such as `[upsteam]` from silently
reverting a whole section to defaults. The only path that accepts unknown keys
is migration with an explicit flag:

```bash
sudo sito config migrate --from v1 --to v2 --backup --ignore-unknown-keys
```

Every dropped key is reported in `unknown_dropped`; it is never preserved and
never silently dropped. If the report is empty and the command still fails, fix
the named key instead of adding the flag.

### 4.3.1 Client group references fail closed

A `[[clients.entries]]` `group` must name an existing
`[clients.groups.<name>]` table, or be omitted/`"default"`. 1.9 silently fell
back to the default policy when the group did not exist; 2.0 reports a
cross-section error on `clients.entries[i].group` during migration, startup,
API writes, backup restore and HA apply (the restore path calls the same
validator). Add the missing group table (or change
the entry to `group = "default"`) before retrying the upgrade.

### 4.4 Safe defaults vs behavior-preserving upgrade

New installs (`Config::default()`) use the 2.0 safe defaults. Migrated v1 files
keep the old effective behavior unless `--adopt-safe-defaults` is passed. See
the [safe-default table](config-v2.md#4-20-safe-defaults). The important
operator-visible defaults are:

| Setting | 1.9 behavior | 2.0 safe default | Upgrade behavior |
|---|---|---|---|
| `web.bind` | `0.0.0.0` | `127.0.0.1` | v1 file keeps/materializes `0.0.0.0`; opt in to loopback |
| `web.metrics_auth` | `true` | `true` | unchanged |
| `filtering.fail_closed` | `true` | `true` | unchanged |
| `acme.allow_bootstrap_cert` | `false` | `false` | unchanged |
| `upstream.allow_private_targets` | `false` | `false` | unchanged |
| `auth.token_default_ttl_days` | `90` | `90` | unchanged |
| `auth.token_max_ttl_days` | (unbounded) | `365` | new 2.0 cap for new tokens; existing tokens keep their expiry |
| `stats.rollup_client_names` | `false` | `false` | unchanged |
| `server.update_require_signature` | `true` | `true` | unchanged |

`dns.bind` remains `["0.0.0.0", "::"]` in 2.0 because a default-deny DNS client
ACL is deferred, not part of Phase 2 core hardening. Keep the DNS ports behind a
host firewall or bind specific LAN addresses. The admin UI is plain HTTP; the
DNS `[tls]` certificate never secures it.

### 4.5 Restart-only fields and the wizard exception

A config write that changes a restart-only field returns **409 Conflict** with
`restart_required` and is **not persisted**. `GET /api/v2/config/restart-required`
previews the matrix; the full list and reasons are in
[`docs/config-v2.md`](config-v2.md#7-restart-only-matrix-d11). In summary:

- process identity: `server.role`, `server.instance_name`, `server.data_dir`,
  `server.log_format`;
- admin listener: `web.enabled`, `web.bind`, `web.port` (other `[web]` keys are
  hot);
- `[tls]`/`[dns.tls]`, `[acme]`, `[auth]`, `[ha]`, `[integrations]`.

Edit `config.toml` and restart, or use the installer. Certificate **contents**
are hot-reloaded by the watcher; changing configured certificate paths is
restart-only.

The first-boot wizard is the one deliberate exception: it completes initial
configuration and reports restart-only fields instead of failing a fresh setup.
It still uses the same validator and matrix.

### 4.6 Rollback

To return to 1.9.x:

```bash
sudo systemctl stop sito
sudo cp -a /etc/sito/config.toml.v1.bak /etc/sito/config.toml
# Restore the previous binary or container image tag, then:
sudo systemctl start sito
```

Restore the data-directory archive too if anything wrote 2.0-only state. The
2.0 tree does not change the SQLite schema, so a 1.9.5 `stats.db` remains usable
after a binary/config rollback. HA protocol v2 *does* change the wire format and
the `ha_state.toml`/`ha_watermark.toml` shape, so an HA rollback also requires
the pre-upgrade state/watermark and certificate backups described in
[§8.2](#82-ha-protocol-v2-upgrade). A future SQLite schema migration would
require restoring its backup; that migration is deferred and not part of the
Phase 2 tree.

### 4.7 Filter and integrations refresh intervals are capped at one year

`filtering.refresh_interval_hours`, each `filtering.lists[].refresh_hours`, the
`integrations.lists.refresh_hours` default and each
`integrations.lists.categories.<name>.refresh_hours` must be between 1 and 8760
(`MAX_REFRESH_HOURS`, one year). A configuration with a larger value now fails
validation at startup, in `check-config`, and on API apply. Lower the value to
8760 or less; the schedulers also clamp and use checked time arithmetic
defensively.

## 5. API changes

### 5.1 `/health` is generic

| Before 2.0 (1.9.x) | After 2.0 |
|---|---|
| Always `200` with `status`, `setup_pending`, `ha`, `acme` | `200 {"status":"ok"}` when ready; `503 {"status":"unavailable"}` when not |

External probes and load balancers must not parse `ha`, `acme` or
`setup_pending` from `/health`; those fields are gone. Use the status code and
the `status` value only. During first-boot setup-pending the DNS listeners are
not bound, so `/health` is unavailable until setup completes; the CLI
`healthcheck --setup-fallback` accepts that window through the setup middleware
signal.

### 5.2 Detailed status endpoints (additive)

`GET /api/v2/status` requires Viewer or higher and keeps the existing
`version`, `uptime_seconds`, `role`, `listeners` and `acme` fields. It adds:

- `ready` — the same aggregate verdict `/health` uses;
- `reasons[]` — `component` (`listeners`, `tls`, `acme`, `ha`, `filter`,
  `stats`), stable `code`, human `message` and optional `since_unix_ms`, in
  component order.

`GET /api/v2/ha/status` requires **Admin** and carries the detailed HA
`ready`/`readiness_reason` (and master `diverged_reason`). A stats
database/writer outage is advisory and does not make DNS unhealthy; a retained
filter snapshot reports `filter_degraded` but stays ready. The full component
matrix and D12 certificate ladder are in the
[HA runbook](runbook-ha.md#health-and-status-endpoint-semantics-wp-17).

`GET /api/v2/config/restart-required` requires **Admin** and is a new read-only
preview of the BC-3 matrix.

### 5.3 API v2

- `/api/v2` is the only mounted administrative API. `/api/v1` was removed in
  2.0.0 and returns `404`; there is no v1 alias, redirect or compatibility
  facade. `test_api_surface_uses_only_v2_and_removes_v1` pins that decision:
  `/api/v2/status` returns `401` without a session and `200` with one,
  `/api/v1`, `/api/v1/status` and `/api/v1/stats` return `404`, and every
  OpenAPI path starts with `/api/v2`.
- The WP-2.11 hardening *is* implemented: OpenAPI security schemes, stable tags,
  the missing WebSocket/alias paths, `no-store`/`Vary: Cookie` responses and
  Origin validation are documented in §26 of the
  [public API diff](2.0-public-api-diff.md#26-api-hardening-openapi-config-apply-updater-wp-211).
- The legacy WebSocket `?token=` query parameter is removed by WP-2.14 (BC-8).
  Use an `Authorization` header or the `__Host-` session cookie; browser
  session clients must also send a same-origin `Origin`.
- The SQLite migration is implemented both as the explicit `sito db migrate`
  ([§6](#6-database)) and as the opt-in startup path controlled by
  `SITO_DB_AUTO_MIGRATE`. Startup fails closed by default. The explicit
  `sito db anonymize --all` command rewrites historical query-log PII; there is
  no automatic anonymization at startup. Installer/Docker config auto-migration
  remains deferred. The CLI config migration in [§4](#4-config-v1--v2) is the
  supported config path.
- The query-log cursor contract, session/reauth behavior, error/status rules
  and copy-paste client examples are in
  [§5.4](#54-client-visible-rest-contract-bc-10).

### 5.4 Client-visible REST contract (BC-10)

BC-10 is the HTTP-client contract for 2.0. The Rust-source changes are BC-6;
the WebSocket query-token removal is BC-8. The exact wire shapes are repeated in
[API diff §27](2.0-public-api-diff.md#27-client-visible-rest-contract-bc-10).

#### 5.4.1 Base path, credentials and re-authentication

- **Base path.** `/api/v2` is the only mounted administrative API. Once setup
  is complete, `/api/v1` and every `/api/v1/...` path return `404` with a
  `ProblemDetails` JSON body; there is no alias, redirect or compatibility
  facade. Delete v1 fallbacks and point monitoring, scripts and reverse-proxy
  rules at `/api/v2`.
- **Login and session.** `POST /api/v2/auth/login` takes
  `{"user":"admin","pass":"..."}`. A successful login returns `200`
  `{"username":"admin","role":"admin","totp_required":false}` and delivers the
  session **only** as an `HttpOnly` cookie; it is never in the JSON body. When
  the request is secure (TLS or a trusted TLS-terminating proxy), the cookie is
  `__Host-sito_session`; on plain HTTP it is `sito_session`. Readers accept both
  names, but a client must send back the one it received. Cookies are
  `HttpOnly; SameSite=Strict; Path=/` and `Secure` on TLS.
- **CSRF.** The non-HttpOnly `sito_csrf` cookie is the double-submit token.
  Cookie-authenticated mutating requests must echo it in `X-CSRF-Token` (or a
  `csrf_token` form field for form posts) and must be same-origin: send an
  `Origin` header (a same-origin `Referer` is the fallback), because a cookie
  session with no `Origin`/`Referer` fails closed. Bearer-token requests do not
  need CSRF and may omit both headers.
- **TOTP.** A TOTP-enrolled login returns `202` with `totp_required:true`; the
  short-lived partial token is the `HttpOnly` `sito_partial` cookie (or the
  `partial_token` field when the client sends
  `X-Sito-Token-Delivery: body`). Complete the login with
  `POST /api/v2/auth/totp/verify` and `{"partial_token":"...","code":"..."}`.
- **Bearer tokens.** Send `Authorization: Bearer sito_...`. Mint a token
  (requires **Admin**) with `POST /api/v2/auth/tokens` and
  `{"name":"querylog-reader","scope":"viewer"}`; the response is `201`
  `{"id":"tok_...","name":"...","scope":"viewer","token":"sito_..."}` and the
  plaintext `token` is shown only once. Creating an **Admin-scoped** token from
  a browser session additionally requires `X-Reauth-Token`; an API-token caller
  is exempt.
- **Re-authentication.** Sensitive session mutations (role changes, Admin
  overrides, Admin creation and Admin-scoped token creation, plus TOTP
  enrollment/disable) require a fresh ticket from
  `POST /api/v2/auth/reauth`:
  `{"password":"...","code":"..."}` (the code is required when TOTP is
  enabled). The response is
  `{"reauth_token":"...","expires_in":300}`; send the ticket as
  `X-Reauth-Token`. It is single-use, bound to the account and session, and
  expires after five minutes. A missing, expired, already-used or
  wrong-session ticket is `401`; API-token callers receive `403` because a
  ticket requires a user session. API tokens also cannot manage TOTP or change
  passwords.
- **No URL credentials.** Session and bearer credentials are not read from a
  query string. In particular, the removed `/api/v2/querylog/stream?token=`
  form is rejected; use the session cookie or `Authorization: Bearer`. Browser
  session upgrades must send a same-origin `Origin`; cross-origin and
  `Origin: null` upgrades are `403`. Rotate any token that was ever placed in a
  URL, proxy access log or reverse-proxy query string.

#### 5.4.2 Query-log cursor contract

`GET /api/v2/querylog` requires **Viewer** or higher and returns one page of
query-log rows, newest first. Pagination is keyset/cursor-only; there is no
offset parameter and no total count in the response.

| Parameter | Type | Contract |
|---|---|---|
| `client` | string | Exact match on `client_ip` **or** `client_name`. |
| `domain` | string | Substring match on `qname`; `%`, `_` and `\` are escaped. |
| `status` | string | Exact `verdict`: `allowed`, `blocked`, `whitelisted`, `rewritten` or `stale`. |
| `qtype` | u16 | Exact numeric record type (for example `1` = A, `28` = AAAA). |
| `from`, `to` | i64 | Inclusive unix-millisecond bounds on `ts`. |
| `limit` | usize | Page size; defaults to **50**, clamped to **1..=500**. |
| `cursor` | string | Opaque value from the previous response's `next_cursor`; omit it for the first (live) page. |

Response shape:

```json
{
  "items": [
    {
      "id": 1042,
      "ts": 1763899200123,
      "client_ip": "192.0.2.10",
      "client_name": "laptop",
      "qname": "example.com",
      "qtype": 1,
      "rcode": 0,
      "verdict": "allowed",
      "upstream": "1.1.1.1",
      "elapsed_us": 1234,
      "dnssec": "secure",
      "proto": "udp"
    }
  ],
  "next_cursor": "AQAAAZqwldJ7AAAAAAAABBIxMjM0NTY3OA"
}
```

`rule`, `list_source`, `client_name`, `rcode`, `upstream`, `elapsed_us` and
`dnssec` are omitted when absent. `next_cursor` is present on every response and
is `null` on the last page.

Cursor rules:

- **Opaque and versioned.** Treat the cursor as an uninterpreted string. Its
  payload is a base64url, versioned `(ts, id)` keyset position plus a filter
  hash; the wire layout may change between releases. Never construct, decode or
  edit one.
- **Filter-bound.** The cursor is bound to `client`, `domain`, `status`,
  `qtype`, `from` and `to` in a fixed order. `limit` is deliberately excluded,
  so you may change the page size while continuing to page. An empty value
  (`?client=`) is a present filter and hashes differently from omitting the
  parameter, so keep the filter query string identical while paging. Changing
  any bound filter invalidates the cursor: replaying it returns `400` and you
  must restart from the first page.
- **Newest first and stable.** Rows are ordered by `(ts, id)` descending; ties
  on `ts` break by `id` descending. The next page starts strictly below the last
  returned row. This is keyset (not snapshot) pagination: rows inserted with a
  newer position are not seen by later pages, deleted rows disappear, and rows
  that remain neither duplicate nor skip.
- **End of history.** Stop when `next_cursor` is `null`. Do not infer the end
  from `items.length < limit` alone and do not ask for a total count; the page
  read intentionally runs no `COUNT(*)`.
- **`400` rules.** A cursor that is not valid base64url, has the wrong payload
  length, has an unsupported version, or does not hash to the current filter set
  is a `400` `application/problem+json`. The filter-mismatch detail is exactly
  `cursor does not belong to the current filter set; restart from the first
  page`.
- **Live tail versus history.** The UI's live refresh sends no cursor and keeps
  the filters stable. "Load older" sends the cursor and pauses live polling;
  changing a filter or refreshing clears the cursor and returns to the live
  first page.

Error and rate-limit behavior:

| Status | When |
|---|---|
| `200` | Page read; `items` + `next_cursor`. |
| `400` | Invalid or filter-mismatched cursor (`application/problem+json`). |
| `401` | No valid session cookie or bearer token. |
| `403` | Authenticated but lacking the required role. |
| `429` | Per-IP query-log budget (120 requests/minute) or the account-wide API budget is exhausted; `Retry-After` is `1` for the query-log budget and up to `60` for the account budget. |
| `500` | The stats database read failed. |

Both limits can apply. Back off for the `Retry-After` interval instead of
retrying immediately; the query-log budget is in addition to the account-wide
`auth.api_rate_limit_per_minute` ceiling (default 600 requests/minute).

#### 5.4.3 Upstream config 308 alias

`GET /api/v2/upstream` and `PUT /api/v2/upstream` are canonical.
`GET /api/v2/upstream/config` and `PUT /api/v2/upstream/config` are permanent
redirects: after Operator authentication they return
`308 Permanent Redirect` with `Location: /api/v2/upstream` and no body.
Authentication is checked **before** the redirect, so an unauthenticated caller
gets `401` (and a caller below Operator gets `403`) rather than a redirect.
Update the path, or use a client that follows `308` while preserving the method
and body (important for `PUT`).

#### 5.4.4 Status, errors and caching

`/health` stays a generic probe (`200 {"status":"ok"}` when ready,
`503 {"status":"unavailable"}` when not; BC-4). Use the authenticated
`GET /api/v2/status` (Viewer) for `version`, `uptime_seconds`, `role`,
`listeners`, `ready` and `reasons[]`. `GET /api/v2/config` (Admin) returns
`{"config_toml":"..."}` with secrets masked; a `500` means the file could not be
read. `GET /api/v2/config/restart-required` (Admin) previews the restart-only
matrix.

Handler-generated errors use RFC 7807 `application/problem+json`. The
unknown-path fallback (`404`, including every `/api/v1...` path) carries the
same `ProblemDetails` body as `application/json`.

```json
{
  "type": "https://sito.network/errors/409",
  "title": "Conflict",
  "status": 409,
  "detail": "the server's explanation",
  "restart_required": ["web.bind"]
}
```

`type`, `title`, `status` and `detail` are always present; `instance` is
optional; `restart_required` appears only on a restart-only `409` and is a JSON
array of dotted field names. The server persists **nothing** when it returns
that `409`. Client-visible statuses:

| Status | Meaning |
|---|---|
| `201` | A create endpoint succeeded (`/clients`, `/clients/groups`, `/filtering/lists`, `/rewrites`, `/auth/users`, `/auth/tokens`); the created DTO is in the body. Accept `201`, not only `200`. |
| `400` | Invalid input, invalid cursor, invalid rewrite/reference or bad token scope; nothing was persisted. |
| `401` | Missing/invalid session or bearer token, invalid login credentials, or a missing/invalid/expired/used `X-Reauth-Token`. |
| `403` | Authenticated but insufficient role, CSRF failure, cross-origin WebSocket, or an API-token caller attempting session re-authentication. |
| `404` | Unknown path; specifically every `/api/v1...` path. The fallback body is the same `ProblemDetails` JSON with `Content-Type: application/json`. |
| `409` | Restart-only config write/restore (with `restart_required`, nothing persisted), referenced group/list conflict, generation conflict, concurrently running update, systemd-managed in-app update, or an unknown version that needs `force`. |
| `429` | Login/lockout, query-log per-IP budget or account-wide API budget; when `Retry-After` is present, wait that long before retrying. |
| `500` | Config file or stats database could not be read; the request did not succeed. |
| `501` | HA endpoint on a build without the `ha` feature (`ha_not_supported`); the route and authorization still run first. |

Authenticated `/api/v2` responses carry `Cache-Control: no-store` and
`Vary: Cookie`; do not cache them in a shared cache. The filtering **UI** reduces
configured filter-list URLs, runtime/integration `source_url` values and URLs
inside refresh errors to scheme+host for roles below Operator; the API JSON
itself is not redacted, and an Operator sees the full source URL in the UI. Do
not build a UI client that requires the full URL from a Viewer session.

#### 5.4.5 Copy-paste curl examples

Login, obtain a one-use re-authentication ticket, then mint an Admin-scoped API
token (use `-c`/`-b` so both the session and CSRF cookies are carried):

```bash
BASE=http://127.0.0.1:8080   # use https:// to receive the __Host- session cookie
JAR=$(mktemp)
curl -sS -c "$JAR" -H 'Content-Type: application/json' \
  -d '{"user":"admin","pass":"change-me"}' \
  "$BASE/api/v2/auth/login" | jq .
CSRF=$(awk '$6 == "sito_csrf" {print $7}' "$JAR")
REAUTH=$(curl -sS -b "$JAR" -H "Origin: $BASE" -H "X-CSRF-Token: $CSRF" \
  -H 'Content-Type: application/json' \
  -d '{"password":"change-me"}' \
  "$BASE/api/v2/auth/reauth" | jq -r .reauth_token)
# Add "code":"123456" to the body above when TOTP is enabled.
TOKEN=$(curl -sS -b "$JAR" -H "Origin: $BASE" -H "X-CSRF-Token: $CSRF" \
  -H "X-Reauth-Token: $REAUTH" -H 'Content-Type: application/json' \
  -d '{"name":"api-admin","scope":"admin"}' \
  "$BASE/api/v2/auth/tokens" | jq -r .token)
```

The re-authentication ticket is single-use and is consumed by the token
creation; request a fresh ticket for another sensitive Admin mutation. The
Admin token can perform every call below (Admin > Operator > Viewer). Use a
Viewer token instead when you only need `GET /api/v2/querylog` or
`GET /api/v2/status`.

First query-log page (default `limit=50`; use `limit=2` to see a cursor on a
small log):

```bash
PAGE1=$(curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/querylog?limit=2")
echo "$PAGE1" | jq .
CURSOR=$(echo "$PAGE1" | jq -r '.next_cursor // empty')
# The 400 example below needs at least three matching rows: with limit=2 a
# cursor is emitted only when a third row exists. Stop if CURSOR is empty.
```

Next page: replay `next_cursor` unchanged. `--data-urlencode` safely carries the
opaque value and you may change `limit` while paging.

```bash
PAGE2=$(curl -sS -H "Authorization: Bearer $TOKEN" --get \
  --data-urlencode "cursor=$CURSOR" \
  --data-urlencode "limit=2" \
  "$BASE/api/v2/querylog")
echo "$PAGE2" | jq .
```

End of history: repeat with each returned `next_cursor`; the final page has
`next_cursor: null` (and may be empty).

```bash
echo "$PAGE2" | jq '{count: (.items | length), next_cursor}'
# The last page looks like {"count":0,"next_cursor":null} or
# {"count":1,"next_cursor":null}; a non-null cursor means fetch the next page.
```

A filter change invalidates the cursor. Reusing it with `status=blocked`
returns `400` with the mismatch detail, so start again without a cursor:

```bash
curl -sS -i -H "Authorization: Bearer $TOKEN" --get \
  --data-urlencode "cursor=$CURSOR" \
  --data-urlencode "status=blocked" \
  "$BASE/api/v2/querylog"
# HTTP/1.1 400 Bad Request
# Content-Type: application/problem+json
# {"type":"https://sito.network/errors/400","title":"Bad Request",
#  "status":400,
#  "detail":"cursor does not belong to the current filter set; restart from the first page"}
```

Status, restart-only preview, and the upstream 308 alias:

```bash
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/api/v2/status" \
  | jq '{version,ready,reasons}'
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/api/v2/config" \
  | jq -r .config_toml | head
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/config/restart-required" | jq .
curl -sS -i -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/upstream/config"
# HTTP/1.1 308 Permanent Redirect
# location: /api/v2/upstream
curl -sS -L -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/v2/upstream/config" | jq .
```

The removed v1 surface is a plain `404`; remove the call rather than retrying:

```bash
curl -sS -i -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/status"
# HTTP/1.1 404 Not Found
# Content-Type: application/json   (unknown-path fallback ProblemDetails)
```

#### 5.4.6 Migration checklist

1. Replace every `/api/v1` base URL with `/api/v2`; delete v1 fallbacks and
   probes. Treat `404` from a v1 path as expected, not a transient failure.
2. Send credentials only in the `Authorization: Bearer` header or the session
   cookie. Remove every `?token=` use; rotate any token that appeared in a URL
   or proxy log.
3. Keep the exact cookie name received (`__Host-sito_session` on TLS,
   `sito_session` on plain HTTP) and preserve `sito_csrf`; send
   `X-CSRF-Token` on cookie-authenticated writes.
4. Replace the old numeric row-id cursor and `entries` page shape with
   `items` + `next_cursor`: first page without a cursor, older pages with the
   previous `next_cursor` unchanged, stop at `null`.
5. Reset to the first page when any of `client`, `domain`, `status`, `qtype`,
   `from` or `to` changes; a reused cursor is a `400`, not a partial page.
6. Accept `201` from create endpoints and parse `application/problem+json` for
   `4xx`/`5xx`; check `Retry-After` on `429` and do not retry a `409`
   restart-only write until the process restarts.
7. Use `/api/v2/upstream` directly or follow the `308` from
   `/api/v2/upstream/config` with the method/body preserved.
8. Update monitoring to use `/health` (200/503) for probes and
   `/api/v2/status` (authenticated) only when detail is needed.

## 6. Database

2.0 records a **schema version marker** in `stats.db`
(`stats_meta.schema_version`). Databases written by 1.9.x do not have the
marker and are therefore **schema version 1**; this build supports **schema
version 2**. Version 2 only adds that marker, the additive `stats_meta` table
and the `idx_ql_ts_id` runtime index; no existing column or row layout changes.
The marker is deliberately not a sqlx migration version, so a 1.9.3/1.9.5
binary can still open an already-migrated database after a rollback.

**Startup policy.** A 2.0 server does **not** migrate silently. On startup it
inspects a private copy of `stats.db` before touching the live file:

- **missing `stats.db`** → normal first install: create the current schema; no
  backup.
- **current schema** → open normally; no backup.
- **older schema with auto-migration disabled** (the default) → refuse to start,
  serve no DNS/API, and write nothing. The error names both supported upgrade
  paths: `sito db migrate` and `SITO_DB_AUTO_MIGRATE=1`.
- **older schema with `SITO_DB_AUTO_MIGRATE=1` (or `true`)** → take the shared
  `<server.data_dir>/db-migrate.lock` (0600, non-blocking), write the same
  consistent 0600 backup as the CLI (refusing to overwrite an existing one),
  migrate, verify that the schema is current, and only then open the runtime
  database and start listeners. Any failure aborts startup, reports the backup
  path, and never serves.
- **newer schema** → refuse without writes; no downgrade.
- **corrupt/unknown marker** → fail closed without writes.

`SITO_DB_AUTO_MIGRATE` accepts only `1`/`true` to enable and unset/empty/`0`/
`false` to disable. Any other value fails startup with an invalid-value error,
so a typo cannot silently select a policy. A server start and
`sito db migrate` use the same migration lock; a second process fails with
“another DB migration is in progress” instead of waiting indefinitely. The
lock is held through inspection, backup, migration and verification.

**Migrating with `sito db migrate`.** The migration is explicit and
forward-only. Stop the service first: the command takes the service lease and
the shared migration lock and refuses to run while a server holds the lease.
There is no `--force` override.

```bash
# 1. Stop the server (migration needs exclusive access to stats.db)
sudo systemctl stop sito

# 2. Inspect the plan (no database writes)
sudo sito db migrate --config /etc/sito/config.toml --dry-run

# 3. Take the backup and migrate
sudo sito db migrate --config /etc/sito/config.toml

# 4. Start the server again
sudo systemctl start sito
```

- `--dry-run` prints the found/supported versions, the target database and the
  backup path, and creates or modifies **no** database, WAL/SHM or backup file.
  It exits 0.
- The real run inspects a private copy of the database before any mutation:
  - **already current** (`schema_version = 2`) → prints “already at schema
    version 2”, exits 0, creates no backup and writes nothing. A second run is
    a safe no-op.
  - **older** (`schema_version = 1`, or no marker) → backs up, then upgrades
    to 2 and prints the resulting version.
  - **newer** (for example a 3.0 database) → refuses with both versions and
    exits non-zero; no database files are changed. **There is no downgrade and
    no `--to`/`--from` flag.**
  - **corrupt or unknown marker** → fails closed with the invalid value; no
    writes.
  - **missing `stats.db`** → clear error. This command never creates an empty
    database; a first install creates it when the server starts.
- Before migrating, a consistent snapshot is written to
  `<server.data_dir>/stats.db.v<found>.bak` (normally
  `/var/lib/sito/stats.db.v1.bak`). It uses SQLite `VACUUM INTO` on a private
  copy of the database (including committed WAL content), never a naive copy
  of a live WAL file, is **mode 0600**, and an existing backup is never
  overwritten: move it aside first.
- The service lease is held for the whole inspect → backup → migrate sequence,
  so a supervisor cannot start the server mid-migration.
- `--no-backup` skips the snapshot. This is **not recommended**: after a failed
  migration the only rollback then is a copy you made yourself.

Running the command with `sudo` is safe for the data directory: before it
returns, it restores the ownership of every file it created or modified
(`stats.db`, its `-wal`/`-shm` sidecars, `stats-salt`, the lease file and the
`.bak`) to the owner of the existing `stats.db`, so the unprivileged `sito`
service can open them again. Running as the service user
(`sudo -u sito sito db migrate ...`) also avoids the issue. If ownership
restoration itself fails, the command prints an error naming the path.

To roll back a database migration, stop the service, remove any `-wal`/`-shm`
sidecars, restore the `.bak` file over `stats.db`, and start the service.

**Retroactive anonymization with `sito db anonymize --all`.** Existing
`query_log` rows written before `privacy.anonymize_querylog` was enabled keep
their raw client IP and client name; enabling the setting is forward-only. The
2.0 command rewrites those historical rows explicitly. It is never run at
startup.

```bash
# 1. Stop the server: anonymization needs exclusive access to stats.db
sudo systemctl stop sito

# 2. Keep a pre-anonymization copy; anonymization cannot be undone
sudo install -d -m 0700 /var/backups/sito-pre-anonymize
sudo tar -C /var/lib/sito -czf /var/backups/sito-pre-anonymize/var-lib-sito.tgz .

# 3. Count the rows that would change (reads a private copy, no live writes)
sudo sito db anonymize --all --config /etc/sito/config.toml --dry-run

# 4. Apply it
sudo sito db anonymize --all --config /etc/sito/config.toml

# 5. Start the server again
sudo systemctl start sito
```

- `--all` is **required** in 2.0: per-client and date-range selection is not
  implemented yet. `--dry-run` reports how many rows would change without
  creating or modifying the live database, its WAL/SHM sidecars or
  `stats-salt`.
- **What changes:** `client_ip` is masked with the same anonymizer the live
  writer uses (IPv4 `/24`, IPv6 `/56`, IPv4-mapped IPv6 as the mapped IPv4
  `/24`, so `192.0.2.10` becomes `192.0.2.0`), and `client_name` is set to
  `NULL`. A malformed stored `client_ip` cannot be masked safely and is left as
  is, but its `client_name` is still cleared and the count is reported.
- **What is preserved:** every row, `id`, `ts`, `qname`, `qtype`, `rcode`,
  `verdict`, `rule`, `list_source`, `upstream`, `elapsed_us`, `dnssec` and
  `proto`. Aggregates in `stats_hourly` are deliberately **not** rewritten:
  their client identifiers are already hashed by the rollup PII backfill and
  the `rollup_client_names` policy owns their scrub.
- Rows are processed in key-ordered chunks of 1,000, one committed transaction
  per chunk, so memory and transaction size stay bounded. A crash or `Ctrl-C`
  loses at most the uncommitted chunk; rerunning the command resumes safely and
  skips rows that already carry a masked address and a `NULL` name.
- The command is **idempotent**: a second run reports `0 changed` and does not
  rewrite or vacuum the database.
- After a full run that changed at least one row, the database is `VACUUM`ed
  and the WAL is truncated. Anonymization is a privacy rewrite, so this runs
  without waiting for the retention threshold: `secure_delete=ON` already
  zeroes overwritten content, and the vacuum/truncate removes old unmasked
  values still reachable through free pages and the WAL. The row count does not
  change, so the file may not shrink much.
- The service lease and the shared `<server.data_dir>/db-migrate.lock` are used
  exactly as for `sito db migrate`. A live server is refused and there is no
  `--force` override; stop the service instead. The schema must already be
  current (run `sito db migrate` first); this command never migrates implicitly.
- The command does not change the schema version and creates no new SQLx
  migration. Running it as `sudo` restores ownership of every file it creates
  or modifies to the owner of the existing `stats.db`.
- **Rollback:** there is no inverse operation that restores the original raw
  addresses and names. Keep the pre-anonymization archive; to revert, stop the
  service, restore `stats.db` (remove its `-wal`/`-shm` first) and start it.

**Mix of `db migrate` and `db anonymize`.** If the database is still schema
version 1, run `sito db migrate --config <path>` first, then
`sito db anonymize --all --config <path>`. The anonymization command refuses an
older, newer or corrupt schema without writing to the database.

**Clearing the query log with `--keep-aggregates`.** `sito clear-query-log
--keep-aggregates` (or `DELETE /api/v2/querylog?keep_aggregates=true`) deletes
the detailed rows only after folding them into `stats_hourly`. It processes the
oldest remaining hour in `(ts, id)` chunks of 5,000 rows, one committed
transaction per chunk, then continues with the next hour. The writer lock is
bounded by one chunk and memory by one chunk of distinct domains, clients and
upstreams; no rollup totals are held for the whole range. A chunk commits only
after its rollup contribution is written, so an interrupted or failed clear
leaves every earlier chunk committed and merely stops before the current one.
Each chunk merges its delta into the current `stats_hourly` row inside the
write transaction, so a resume keeps the top lists accumulated by committed
chunks and a concurrent retention update is preserved. Running the same command
again resumes from the oldest remaining row and finishes the clear without
double counting; a completed clear followed by new rows (including backdated
rows) is also safe to clear again. A deleted rollup row is not resurrected, and
a zero-row chunk never creates an empty rollup. When the clear completes it runs
`VACUUM` and truncates the WAL if the run removed at least 1,000 rows, or if the
completing run emptied the detailed log (so a clear resumed in several
sub-threshold runs still vacuums). A smaller clear relies on `secure_delete=ON`
because rewriting the whole database file would cost more than it reclaims.
`stats_watermark` is still written as a diagnostic but is never read to skip
rows.

**Stopped CLI vs live API/UI clear.** Stop the service before running
`sito clear-query-log --keep-aggregates`: the CLI holds the service lease and
refuses a live server (unless `--force`, which bypasses the lease). With a live
producer a row inserted after its hour was processed can survive until the next
clear/retention. The API and UI clear necessarily run against the live server;
it is still safe with the retention scheduler because both paths share an
in-process maintenance lock and each chunk merges the live rollup row, but a
complete guaranteed-empty log requires the stopped CLI path.

**Installer and Docker upgrades.** Both supported package paths run the explicit
`sito db migrate` command rather than opting the server into
`SITO_DB_AUTO_MIGRATE`:

- `contrib/install.sh` runs `sito db migrate --config /etc/sito/config.toml`
  after stopping the old service and installing the new binary, before starting
  the new service, but only for a 2.0-or-newer target. A 1.9.x → 1.9.x update
  skips it. This requires a config v2 document (see §4). If the config is still
  v1, the installer keeps the new 2.0 binary installed, stops the service, and
  prints the runnable `config migrate` command instead of rolling back to a
  binary that cannot run it. On a failed migration it restores the newly written
  B2 backup before rolling back; if no single new backup exists, it keeps the
  2.0 binary installed and the service stopped with recovery instructions.
- The container image entrypoint runs the same command before the server when
  the data volume already has `stats.db`; a failed migration exits the container
  without serving. A fresh volume creates the current schema normally.

Both paths write the same 0600 `<server.data_dir>/stats.db.v<found>.bak`
(normally `/var/lib/sito/stats.db.v1.bak`). Pass `--no-migrate` to the installer
or set `SITO_NO_MIGRATE=1` for the container to skip the automatic step. The
installer writes `SITO_DB_AUTO_MIGRATE=0` to `/etc/sito/sito.env` so a preserved
B3 opt-in cannot override the no-migrate choice; the container entrypoint
rejects the conflicting `SITO_NO_MIGRATE=1` + `SITO_DB_AUTO_MIGRATE=1` pair.
With only the opt-out set, the server keeps the default fail-closed B3 policy:
it refuses an old database and names `sito db migrate` and
`SITO_DB_AUTO_MIGRATE=1`. The entrypoint itself never sets
`SITO_DB_AUTO_MIGRATE`; startup auto-migration remains an explicit operator
opt-in.

A pre-2.0 rollback is only restarted with a matching v1 config: the installer
uses `<config>.v1.bak` (from `sito config migrate --backup`) when the target
configuration is v2, and otherwise keeps the 2.0 binary installed with the
service stopped. After a successful migration the database stays at schema
version 2, which is additive and readable by 1.9.x; use the database rollback
above only when you deliberately need the old schema.

The following privacy/retention behavior is already implemented (the 1.9.4
controls plus WP-2.12) and is documented in
the [configuration reference](configuration-reference.md#12-stats--metrics-and-query-logging):

- keyed BLAKE3 client-IP hashes using `<data_dir>/stats-salt` (0600);
- optional rollup client names (`stats.rollup_client_names = false` by
  default) and rollup retention (`stats.rollup_retention_days`);
- “clear query log” deleting `query_log` and `stats_hourly` by default, with
  `--keep-aggregates` (CLI) / `?keep_aggregates=true` (API) as the explicit
  preserve option; the keep-aggregates clear is chunked (5,000 rows per
  committed `(ts, id)` chunk) and safely resumable after an interruption;
- `secure_delete=ON` and the vacuum/WAL-truncate policy after large clears;
- one-time hashing of existing legacy rollups at startup.

## 7. RouterOS optional integration

RouterOS lease sync moved out of `sito-clients` into the optional
`sito-routeros` crate. **The default `sito` build does not link it.**

```bash
cargo build -p sito                       # default: no sito-routeros
cargo build -p sito --features routeros   # optional integration included
```

A build without the feature rejects `[integrations.mikrotik] enabled = true`
at startup, in `check-config` and on API writes, naming the missing feature. A
disabled section is accepted in every build. The integration remains
**experimental**.

Lease identity requires **both** `https://` and certificate verification
(`allow_invalid_certs = false`). A plaintext `http://` URL or
`allow_invalid_certs = true` marks leases unverified: they are display-only and
never grant a client entry’s group, trusted flag or MAC identity. A configured
but unresolvable
`token_env` fails instead of falling back to basic auth; environment proxies
are disabled and response bodies are capped.

Moved/renamed items (`RouterOsError`, `fetch_routeros_leases`,
`spawn_routeros_sync`, `RawRouterOsLease`, `build_routeros_client`, the request
timeout) are listed in the [public API diff](2.0-public-api-diff.md#1-routeros-is-now-an-optional-crate).
`fetch_routeros_leases` now takes only `&RouterOsConfig` and builds the client
from it; the client parameter was removed so an insecure caller cannot receive
identity-capable leases. `RouterOsConfig` and `RouterOsLease` stay in
`sito-clients`.

> The wire path is closed, not the Rust type: `RawRouterOsLease::into_lease`
> and the `RouterOsLease::verified` field remain public for in-process parsing
> and display. Code that constructs `RouterOsLease` directly is responsible for
> setting `verified`; only the shipped fetch/sync path proves the peer.

## 8. HA

**Phase 2 implements HA protocol v2.** Existing mTLS WebSocket replication,
Ed25519-signed bundles, BLAKE3 certificate pinning and term/version ordering
remain, but v1 peers and v1 state files are deliberately refused. The only 2.0
health change is BC-4: `/health` is generic; read `GET /api/v2/ha/status` for
`ready`/`readiness_reason`/`diverged_reason`. Pinning, CA/SAN and resync
semantics are documented in the
[HA runbook](runbook-ha.md#6-security-considerations-transport-security-certificate-pinning--authentication).

The signed bundle now binds a BLAKE3 `config_digest` and the master's
`signing_key_fingerprint`; the slave verifies both (plus `protocol_version`)
before applying. `ha_watermark.toml` stores the fingerprint and a digest of the
**shared projection** of the applied document: shared-field edits are drift and
require a full apply, while node-local edits (identity, `[ha]`, listener/TLS,
web bind settings, MikroTik credentials and per-client secrets) do not. This is
still **post-edit drift detection**, not edit-time prevention.

### 8.1 Build and feature migration

HA is now an optional Cargo feature. How the binaries are built and what a
no-HA build rejects changed. The `[ha]` key names, certificate generation and
overall readiness semantics remain recognizable, but the wire protocol, signed
bundle identity and on-disk state/watermark format changed to v2
([§8.2](#82-ha-protocol-v2-upgrade)); v1 peers and v1 state files are refused.

| Installation | Action |
|---|---|
| Official release archive / installer | None. The published binaries are built with `embed-ui,ha,mimalloc` and keep HA support. |
| Official container image | None. The image is built with `embed-ui,ha,mimalloc` and keeps HA support. |
| Source build | Add `ha` to the feature set: `cargo build --release --locked --features "embed-ui,ha,mimalloc"`. A plain `cargo build -p sito` is a no-HA binary. |
| Custom embedder of `sito-api` | Depend on `sito-ha-types` for contract types. Do not enable `sito-api/ha` directly; it is internal to `sito/ha`. |

The no-HA build is **fail-closed**, not a silent downgrade:

- startup, `sito check-config`, API config writes and backup restore reject
  `[ha]` and `server.role = "slave"` with an error naming the `ha` feature;
- `/api/v2/ha/status`, `/api/v2/ha/slaves` and `POST /api/v2/ha/resync` stay
  mounted but return `501 ha_not_supported`;
- HA never gates `/health` or `/api/v2/status`;
- `sito ha gen-certs` is absent, because the `ha` subcommand is compiled out.

The portable contract types live in the always-available `sito-ha-types` crate;
`sito-ha` remains the implementation and re-exports the historical paths
(`sito_ha::HaConfig`, `sito_ha::HaMessage`, `sito_ha::ConfigBundle`,
`sito_ha::HaReadiness`, and the rest). Source consumers do not need to change
imports unless they want the dependency-free crate. HA test suites and
`fixtures::ha::FakeMaster` require `cargo test -p sito-test --features ha`
(`--all-features` also works); the default test harness does not link
`sito-ha`.

### 8.2 HA protocol v2 upgrade

**HA protocol v2 is implemented.** It is a coordinated cluster change; a v1
node and a v2 node refuse each other rather than misinterpreting state.

What changed:

- `protocol_version = 2` in `Hello` and `ConfigPush`. A `Hello` without the
  field is treated as v1 and rejected with a `protocol_mismatch` close reason,
  log error, slave readiness reason and
  `sito_ha_protocol_rejections_total{role,reason}` counter.
- The signed `ConfigBundle` requires `protocol_version`, a BLAKE3
  `config_digest` of `config_toml`, and the master's
  `signing_key_fingerprint`. The slave verifies all three against the configured
  `master_pubkey`; identity-less or mismatched payloads are refused.
- `ha_state.toml` and `ha_watermark.toml` use a wrapped v2 shape with a required
  `protocol_version`. A v1 file is refused with migration instructions; it is
  never silently read or reset. Back it up and move it aside before the first
  v2 start. The watermark persists the signing-key fingerprint, so a same-term
  key change requires an explicit higher-term promotion.
- `PublishOutcome::Published` reports `slaves_connected`, `slaves_queued` and
  `slaves_coalesced`; the API status is `queued` when something was enqueued and
  `connected_no_delivery` when peers are connected but no channel accepted the
  push. Neither is delivery proof; that is the slave ACK
  (`GET /api/v2/ha/slaves`).
- Bracketed IPv6 master URLs are supported
  (`master_url = "wss://[2001:db8::10]:8953"`).
- A configured certificate pin or CA is always enforced; CA-only is valid,
  `allow_unpinned_tls` only opts into no verification when neither is set.
  Reusing a CA repairs `ca.key` to `0600`.
- Limits are explicit: 1 MiB message/frame, 4 MiB per-slave queue, 10 s send
  and handshake deadlines, 64 global/8 per-IP concurrent sessions (the per-IP
  permit is held for the whole session). `TooLarge` is not retried because
  retrying the same document cannot shrink it.

WP-3.2 runs the five rejection tests in `scripts/test-ha-v1-compat.sh`.
`sito-ha` has no feature gate of its own (the `ha` feature belongs to `sito`
and `sito-api`), so the script builds the package as-is. There is deliberately
no two-node v1/v2 E2E: the upgrade is coordinated, not mixed-version.

Before the first v2 start, stop the service, back up `ha_state.toml` on the
master and `ha_watermark.toml` on every slave, then move them aside (for
example to `*.v1.bak`). There is no in-place state-migration command. This
intentionally resets the master sequence to its configured initial values,
resets each slave's local replay guard, and requires a full resync/full apply
from the master. Keep the v1 files for downgrade; do not let a v2 node read
them.

Upgrade order is **master first**, then slaves one node at a time. Replication
is intentionally degraded during the window; DNS keeps answering from each
node's last applied configuration. After starting the master with the state
file moved aside, republish the current bundle (or trigger
`POST /api/v2/ha/resync`) and verify each slave reaches `Synced` with the
master's current term/version via `GET /api/v2/ha/status`.

Downgrade is **not supported in place**. Stop every node, restore the
pre-upgrade backups of `config.toml`, `ha_state.toml`, `ha_watermark.toml` and
the certificate/key material, then start the old binary. A v1 node cannot read
a v2 state/watermark file, and deleting it loses the replay guard.

Edit-time read-only enforcement for shared config fields on slaves remains
**not implemented**; the server detects shared-field drift after the write and
requires a full apply. Node-local fields stay editable and are excluded from
the stored shared-projection digest. See the
[HA runbook §7](runbook-ha.md#7-ha-protocol-v2-upgrade-and-downgrade) for the
step-by-step procedure and the node-local field list.

## 10. Rollback and known issues

- **Config rollback:** restore `<config>.v1.bak` (or the full archive) and the
  previous binary. A 2.0 config is not readable by 1.9.x; a 1.9 config is
  readable by 2.0 only after migration.
- **Binary rollback:** keep the old binary or container tag. The installer
  backs up the binary and config, only restores a pre-2.0 binary together with
  its matching `<config>.v1.bak`, and otherwise keeps the 2.0 binary installed
  with the service stopped.
- **Database/HA:** schema version 2 is additive, so a migrated 1.9.5 data
  directory can be opened by 1.9.5 after a binary/config rollback. The installer
  restores the new B2 `stats.db.v1.bak` before a failed-migration rollback; the
  1.9.3 exact-schema fixture covers the same compatibility guarantee.
  `scripts/test-migration-1.9.5.sh`
  exercises the full restore-and-restart rollback. HA protocol v2 is not
  rollback-safe in place: restore the pre-upgrade `ha_state.toml`,
  `ha_watermark.toml` and certificate backups before starting a v1 binary (see
  [§8.2](#82-ha-protocol-v2-upgrade)). A future SQLite schema migration will
  require restoring its backup; that work is deferred.
  **Anonymization rollback** is restore-only: `sito db anonymize --all` has no
  inverse. Keep a pre-anonymization copy of `stats.db` (or the data directory);
  restoring that backup is the only way to recover raw client IPs/names.
- **Health probes:** consumers that parsed `ha`, `acme` or `setup_pending` from
  `/health` will break. Move them to the status code/`status` field and, where
  authenticated detail is needed, `/api/v2/status` or `/api/v2/ha/status`.
- **Restart-only writes:** a 409 does not mean the write partially applied; the
  document is untouched. Change the file and restart.
- **Unknown-key migration:** `--ignore-unknown-keys` is a one-way, reported
  drop. Keep the report with the backup.
- **Benchmark gate:** `bench.yml` runs nightly on GitHub-hosted `ubuntu-24.04`
  and fails on a >10% regression against the committed
  `benches/baseline.json` (`environment: github-ubuntu-24.04`). A local
  comparison on different hardware is reference-only (`--reference-only`) and is
  not the release gate; regenerate the baseline through the GitHub-hosted
  `update_baseline=true` workflow. See [docs/benchmarks.md](benchmarks.md) and
  [docs/ci.md](ci.md#benchmark-baseline).

# Migrating to sito 2.0

This is the upgrade guide for the **2.0.0-alpha.1** development line and the
planned 2.0 releases. It covers the Phase 1 foundations that are implemented on
this branch and clearly labels the Phase 2 work that is **not yet implemented**.

## 1. Status and scope

| Line | Status | What it means for you |
|---|---|---|
| **1.9.5** | Published stable release | Keep this tag pinned until you deliberately move to the 2.0 line. |
| **2.0.0-alpha.1** | Development line on `main` | Phase 1 foundations only. No stable 2.0 artifact is published; build from source or use a prerelease image. |
| **2.0.0 stable** | Planned | Requires the Phase 2 migrations below plus the Phase 3 release work. |

Phase 1 is implemented on this branch:

- config v2 with one validator and `sito config migrate` (WP-1.3);
- one staged runtime generation and atomic apply (WP-1.4);
- module splits with source-compatible re-exports (WP-1.5);
- one response shaper and cache TTL re-clamping (WP-1.6);
- generic `/health` plus detailed readiness (`/api/v1/status`) (WP-1.7);
- deterministic test harness/clock and shared fixtures (WP-1.8);
- fuzz, benchmark, coverage and dependency-hygiene gates (WP-1.9);
- normalized domain/client identity and optional RouterOS (WP-1.1/1.2).

**Not implemented in Phase 1** (all marked planned below): API v2 and the
`/api/v2` prefix, WebSocket `?token=` removal, the SQLite schema/PII migration
with `sito db migrate`/`SITO_DB_AUTO_MIGRATE`, and HA wire protocol v2. Do not
follow those procedures against this branch.

## 2. Before you upgrade

1. Read the [breaking-change index](#3-breaking-change-index).
2. Stop the service so no process holds the config, database or service lease.
3. Back up the whole data directory **and** the configuration, including
   `config.toml`, `users.toml`, `totp.key`, `stats.db`, `stats-salt`, the ACME
   cache, HA certificates/key material, `ha_state.toml` and
   `ha_watermark.toml`:

   ```bash
   sudo systemctl stop sito
   sudo install -d -m 0700 /var/backups/sito-pre-2.0
   sudo tar -C /etc/sito -czf /var/backups/sito-pre-2.0/etc-sito.tgz .
   sudo tar -C /var/lib/sito -czf /var/backups/sito-pre-2.0/var-lib-sito.tgz .
   ```

4. Keep the previous **binary** (or container image tag) in the backup. A config
   rollback alone is not a complete rollback.

`--backup` on the migration command writes a private `config.toml.v1.bak`
(mode `0600`) next to the config; the full archive above additionally covers
the data directory.

## 4. Config v1 → v2

### 4.1 Run the migration

Only a `v1` → `v2` migration is supported. The command is explicit; the
installer/Docker auto-migration and `--no-migrate` are Phase 2 work (WP-2.13)
and are **not implemented on this branch**.

```bash
sudo systemctl stop sito
sudo sito config migrate --from v1 --to v2 --backup --config /etc/sito/config.toml
sudo systemctl start sito
```

`--from`/`--to` are required and only `v1` → `v2` is accepted. With
`--backup`, the original document is written atomically to
`<config>.v1.bak` (mode `0600`) before the replacement. The replacement is
written to a private sibling, fsynced and renamed, also `0600`.

The migration is **behavior-preserving** by default:

1. it parses the v1 document and rejects unknown keys unless
   `--ignore-unknown-keys` is given;
2. it copies every known v1 key/value, even when the 2.0 default differs;
3. it moves `[dns.tls]` into typed `[tls]`;
4. it moves `[web] acme_*` into typed `[acme]` (an existing canonical value
   wins and the conflict is reported);
5. it rewrites `stats.query_log_retention_days` → `stats.retention_days` and
   `privacy.anonymize_client_ip` → `privacy.anonymize_querylog`;
6. it drops removed/dead keys and reports them;
7. it writes `config_version = 2` and validates the result with the normal v2
   parser before the file is replaced.

The checked-in [`config-v1-to-v2-map.toml`](../crates/sito-core/config-v1-to-v2-map.toml)
enumerates every serde field and is embedded in the binary. A unit test
(`config::tests::test_config_map_covers_every_serde_field`) fails when the map
and schema diverge. The docs checker additionally verifies that every kept map
path and every deprecated alias target is documented in the configuration
reference.

### 4.2 Read the report

`--json` prints a machine-readable report:

```json
{
  "from_version": 1,
  "to_version": 2,
  "moved": [
    { "from": "web.acme_enabled", "to": "acme.enabled", "reason": "..." }
  ],
  "removed": [
    { "from": "auth.admin_password_hash", "reason": "..." }
  ],
  "unknown_dropped": [],
  "defaults_materialized": ["web.bind"],
  "safe_defaults_applied": [],
  "warnings": []
}
```

- `moved` lists aliases rewritten to their canonical path.
- `removed` lists keys rejected in v2 (`auth.admin_password_hash`,
  `auth.tokens`, `integrations.mikrotik.token`) and any v2-dead key.
- `unknown_dropped` is non-empty only with `--ignore-unknown-keys`.
- `defaults_materialized` lists values written to preserve v1 behavior (for
  example an omitted `web.bind`).
- `safe_defaults_applied` lists fields changed by `--adopt-safe-defaults`.
- `warnings` names alias conflicts and other review items.

### 4.3 Unknown keys and typos

Startup, `check-config`, API writes, backup restore and HA apply reject unknown
keys/tables by default. This prevents a typo such as `[upsteam]` from silently
reverting a whole section to defaults. The only path that accepts unknown keys
is migration with an explicit flag:

```bash
sudo sito config migrate --from v1 --to v2 --backup --ignore-unknown-keys
```

Every dropped key is reported in `unknown_dropped`; it is never preserved and
never silently dropped. If the report is empty and the command still fails, fix
the named key instead of adding the flag.

### 4.4 Safe defaults vs behavior-preserving upgrade

New installs (`Config::default()`) use the 2.0 safe defaults. Migrated v1 files
keep the old effective behavior unless `--adopt-safe-defaults` is passed. See
the [safe-default table](config-v2.md#4-20-safe-defaults). The important
operator-visible defaults are:

| Setting | 1.9 behavior | 2.0 safe default | Upgrade behavior |
|---|---|---|---|
| `web.bind` | `0.0.0.0` | `127.0.0.1` | v1 file keeps/materializes `0.0.0.0`; opt in to loopback |
| `web.metrics_auth` | `true` | `true` | unchanged |
| `filtering.fail_closed` | `true` | `true` | unchanged |
| `acme.allow_bootstrap_cert` | `false` | `false` | unchanged |
| `upstream.allow_private_targets` | `false` | `false` | unchanged |
| `auth.token_default_ttl_days` | `90` | `90` | unchanged |
| `stats.rollup_client_names` | `false` | `false` | unchanged |
| `server.update_require_signature` | `true` | `true` | unchanged |

`dns.bind` remains `["0.0.0.0", "::"]` in 2.0 because a default-deny DNS client
ACL is not part of Phase 1. Keep the DNS ports behind a host firewall or bind
specific LAN addresses. The admin UI is plain HTTP; the DNS `[tls]` certificate
never secures it.

### 4.5 Restart-only fields and the wizard exception

A config write that changes a restart-only field returns **409 Conflict** with
`restart_required` and is **not persisted**. `GET /api/v1/config/restart-required`
previews the matrix; the full list and reasons are in
[`docs/config-v2.md`](config-v2.md#7-restart-only-matrix-d11). In summary:

- process identity: `server.role`, `server.instance_name`, `server.data_dir`,
  `server.log_format`;
- admin listener: `web.enabled`, `web.bind`, `web.port` (other `[web]` keys are
  hot);
- `[tls]`/`[dns.tls]`, `[acme]`, `[auth]`, `[ha]`, `[integrations]`.

Edit `config.toml` and restart, or use the installer. Certificate **contents**
are hot-reloaded by the watcher; changing configured certificate paths is
restart-only.

The first-boot wizard is the one deliberate exception: it completes initial
configuration and reports restart-only fields instead of failing a fresh setup.
It still uses the same validator and matrix.

### 4.6 Rollback

To return to 1.9.x:

```bash
sudo systemctl stop sito
sudo cp -a /etc/sito/config.toml.v1.bak /etc/sito/config.toml
# Restore the previous binary or container image tag, then:
sudo systemctl start sito
```

Restore the data-directory archive too if anything wrote 2.0-only state. The
2.0 branch does not change the SQLite schema or HA wire protocol, so the same
data directory remains usable by 1.9.5; this is not a promise for the planned
Phase 2 migrations. Downgrade is not supported in place for Phase 2 HA v2 or a
future schema migration.

## 5. API changes

### 5.1 `/health` is generic

| Before 2.0 (1.9.x) | After 2.0 |
|---|---|
| Always `200` with `status`, `setup_pending`, `ha`, `acme` | `200 {"status":"ok"}` when ready; `503 {"status":"unavailable"}` when not |

External probes and load balancers must not parse `ha`, `acme` or
`setup_pending` from `/health`; those fields are gone. Use the status code and
the `status` value only. During first-boot setup-pending the DNS listeners are
not bound, so `/health` is unavailable until setup completes; the CLI
`healthcheck --setup-fallback` accepts that window through the setup middleware
signal.

### 5.2 Detailed status endpoints (additive)

`GET /api/v1/status` requires Viewer or higher and keeps the existing
`version`, `uptime_seconds`, `role`, `listeners` and `acme` fields. It adds:

- `ready` — the same aggregate verdict `/health` uses;
- `reasons[]` — `component` (`listeners`, `tls`, `acme`, `ha`, `filter`,
  `stats`), stable `code`, human `message` and optional `since_unix_ms`, in
  component order.

`GET /api/v1/ha/status` requires **Admin** and carries the detailed HA
`ready`/`readiness_reason` (and master `diverged_reason`). A stats
database/writer outage is advisory and does not make DNS unhealthy; a retained
filter snapshot reports `filter_degraded` but stays ready. The full component
matrix and D12 certificate ladder are in the
[HA runbook](runbook-ha.md#health-and-status-endpoint-semantics-wp-17).

`GET /api/v1/config/restart-required` requires **Admin** and is a new read-only
preview of the BC-3 matrix.

### 5.3 Phase 2 API work (not implemented)

- `/api/v2` is **not present** on this branch. `/api/v1` remains canonical.
  The planned 2.0 API work adds `/api/v2`, keeps `/api/v1` as a compatibility
  facade for one alpha, and removes the facade at 2.1.0.
- OpenAPI per-operation `security` arrays already exist; the reusable
  `components.securitySchemes` block and the config-schema endpoint are planned
  Phase 2 work.
- WebSocket `?token=` removal is planned Phase 2 work. On this branch the
  documented `Authorization`/cookie + Origin path is the supported one; the
  deprecated query parameter remains a known limitation until the Phase 2
  change lands.

## 6. Database

**Phase 1 does not change the SQLite schema.** A 1.9.5 `stats.db` opens on this
branch without a migration step. The following privacy/retention behavior is
already implemented (the 1.9.4 controls) and is documented in the
[configuration reference](configuration-reference.md#12-stats--metrics-and-query-logging):

- keyed BLAKE3 client-IP hashes using `<data_dir>/stats-salt` (0600);
- optional rollup client names (`stats.rollup_client_names = false` by
  default) and rollup retention (`stats.rollup_retention_days`);
- “clear query log” deleting `query_log` and `stats_hourly` by default, with
  `--keep-aggregates` (CLI) / `?keep_aggregates=true` (API) as the explicit
  preserve option;
- `secure_delete=ON` and the vacuum/WAL-truncate policy after large clears;
- one-time hashing of existing legacy rollups at startup.

The genuinely missing **Phase 2** database work is:

- an explicit startup schema check/gate (`sito db migrate` or
  `SITO_DB_AUTO_MIGRATE=1` for a v1.9 database);
- an automatic `stats.db` backup before a migration;
- forward-only migration gating (rollback = restore the backup; a newer
  unknown schema is refused);
- `sito db anonymize --all` for retroactive anonymization of existing raw
  `query_log` rows (forward-only by default).

Do not run `sito db migrate` on this branch; the command is part of the Phase 2
work. *(Planned ID: P2-DB.)*

## 7. RouterOS optional integration

RouterOS lease sync moved out of `sito-clients` into the optional
`sito-routeros` crate. **The default `sito` build does not link it.**

```bash
cargo build -p sito                       # default: no sito-routeros
cargo build -p sito --features routeros   # optional integration included
```

A build without the feature rejects `[integrations.mikrotik] enabled = true`
at startup, in `check-config` and on API writes, naming the missing feature. A
disabled section is accepted in every build. The integration remains
**experimental**.

Lease identity requires **both** `https://` and certificate verification
(`allow_invalid_certs = false`). A plaintext `http://` URL or an insecure-TLS
client marks leases unverified: they are display-only and never grant a client
entry’s group, trusted flag or MAC identity. A configured but unresolvable
`token_env` fails instead of falling back to basic auth; environment proxies
are disabled and response bodies are capped.

Moved/renamed items (`RouterOsError`, `fetch_routeros_leases`,
`spawn_routeros_sync`, `RawRouterOsLease`, `build_routeros_client`, the request
timeout) are listed in the [public API diff](2.0-public-api-diff.md#1-routeros-is-now-an-optional-crate).
`RouterOsConfig` and `RouterOsLease` stay in `sito-clients`.

## 8. HA

**Phase 1 does not change the HA wire protocol.** Existing mTLS WebSocket
replication, Ed25519-signed bundles, BLAKE3 certificate pinning, term/version
ordering, the watermark and the `3 × ping_interval_secs` master-loss deadline
continue to work. The only 2.0 health change is BC-4: `/health` is generic;
read `GET /api/v1/ha/status` for `ready`/`readiness_reason`/`diverged_reason`.
Pinning, CA/SAN and resync semantics are documented in the
[HA runbook](runbook-ha.md#6-security-considerations-transport-security-certificate-pinning--authentication).

Phase 1 already records a BLAKE3 digest of the applied `config.toml` in
`ha_watermark.toml`. The watcher checks it against the live file
(`SlaveStatusTracker::verify_applied_config`), and a local edit/revert marks the
node `Degraded` and requires a full apply/resync before it can report `Synced`
again. That is **post-edit drift detection**, not edit-time prevention.

The planned **HA protocol v2** is **not implemented**:

- `protocol_version = 2` in the wire handshake and in `ha_state.toml` /
  `ha_watermark.toml`; v1 peers are rejected with `protocol_mismatch` and a
  readiness reason;
- upgrade order is **master first**, then slaves, one node at a time, with
  replication intentionally degraded during the window;
- downgrade is **not supported in place**; restore the pre-upgrade backup of
  `config.toml`, `ha_state.toml`, `ha_watermark.toml` and certificates, then run
  the old binary;
- edit-time read-only enforcement for shared config fields on slaves (the API
  should reject the write), while node-local fields stay editable. Phase 1 only
  detects the resulting drift after the file/API write.

Do not attempt a v2 upgrade or edit a `protocol_version` field on this branch.
*(Planned ID: P2-HA.)*

## 10. Rollback and known issues

- **Config rollback:** restore `<config>.v1.bak` (or the full archive) and the
  previous binary. A 2.0 config is not readable by 1.9.x; a 1.9 config is
  readable by 2.0 only after migration.
- **Binary rollback:** keep the old binary or container tag. The installer
  backs up the binary and config and restores both on a failed health check.
- **Database/HA:** Phase 1 leaves both unchanged, so a 1.9.5 data directory
  can be reused after a binary/config rollback. This does not apply after the
  planned Phase 2 migrations.
- **Health probes:** consumers that parsed `ha`, `acme` or `setup_pending` from
  `/health` will break. Move them to the status code/`status` field and, where
  authenticated detail is needed, `/api/v1/status` or `/api/v1/ha/status`.
- **Restart-only writes:** a 409 does not mean the write partially applied; the
  document is untouched. Change the file and restart.
- **Unknown-key migration:** `--ignore-unknown-keys` is a one-way, reported
  drop. Keep the report with the backup.
- **Benchmark gate:** the nightly benchmark comparison requires a dedicated
  runner and a baseline generated there; the committed baseline is a
  development-host baseline, so the gate is inactive until the runner is
  provisioned. See [docs/benchmarks.md](benchmarks.md) and
  [docs/ci.md](ci.md#benchmark-baseline).

## 11. Verification after migration

```bash
sudo sito check-config --config /etc/sito/config.toml
sudo sito --config /etc/sito/config.toml healthcheck
curl -fsS http://127.0.0.1:8080/health
curl -fsS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/status | jq .
```

Expected: `check-config` accepts `config_version = 2`; `healthcheck` succeeds
after DNS/setup is ready; `/health` is `{"status":"ok"}` with a 200 (or 503
`unavailable` with the reason on `/api/v1/status`). Then run the repository
gates:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-features --all-targets -- -D warnings
cargo test --workspace --all-features --locked
cargo deny check
python3 scripts/check_config_reference.py --github
python3 scripts/check_migration_guide.py --github
python3 scripts/check_markdown_links.py
```
